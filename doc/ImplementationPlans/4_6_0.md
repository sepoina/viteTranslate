# Piano di implementazione 4.6.0 — revisione dei comandi LLM

> [!NOTE]
> **Per il revisore umano**
> - **Namespace unico `--llm-*`** per ogni flag LLM: `translate`, `retranslate`, `context`, `dry-run`,
>   `status`, `auto` (era `--force`), `noask` (era `--yes`), `key-set|key-status|key-clear`, `debug`.
> - **I vecchi flag spariscono senza alias né errore** (scelta dell'utente): `--translate` diventa un flag
>   sconosciuto e la CLI fa una sync normale. È una rottura rispetto alla 4.5.0 → da dire nel changelog.
> - **Un `--llm-qualcosa` sconosciuto invece è un errore**: il prefisso definisce il namespace, e un refuso lì
>   dentro (`--llm-tranlate`) non deve diventare una sync silenziosa.
> - **`--llm-status` assorbe `--context --show`**: stampa anche l'abstract. **Proposta non richiesta**:
>   `--ping` diventa `--llm-ping` (= status + una chiamata minima), altrimenti sparirebbe senza sostituto.
> - **`llm.costGuard: n`**: stima < n → nessuna domanda, anche senza TTY. La guardia CI resta. Senza i due
>   prezzi è un errore di config, come `maxCostPerRun`.
> - **`--llm-debug`**: una cartella `<localeDir>/.llm/YYMMDDHHmmss/` con un file numerato per ogni domanda,
>   risposta, errore (anche i tentativi di retry e i rifiuti del validatore). Si auto-esclude da git.
> - **Bug preesistente corretto**: rifiuti, "declined" e "nothing to do" oggi non stampano niente ed escono 0.

> [!TIP]
> **Log delle sette fasi**
> - Nessuna ambiguità imprevista; unico ask: versione → **4.6.0** (proposta del piano).
> - Test: 52/52 · 1718 asserzioni prima → **53/53 · 1785** dopo (nuovo `llmDebug.test.mjs` + casi
>   D/D-trace/P nei test esistenti).
> - Bundle: runtime invariato (`4254 B` gzip). Plugin cresce solo di `costGuard`; verificato per
>   grep che `debugTrace.js`/`fetchDriver.js`/`callModel.js` non ci finiscono dentro (`lib/dist/`
>   non è versionato, niente diff in byte).
> - Non verificato: nessuna chiamata di rete vera (`--llm-ping` reale saltato su richiesta
>   dell'utente, per non spendere — coperto dai test col driver finto).
> - Demo: la frase in `src/App.jsx` che nomina il comando è cambiata → quella chiave torna `null`
>   nelle tre lingue alla prossima sync. Serve un `--llm-translate` per rimetterla a posto: costa,
>   non l'ho lanciato io.

> [!IMPORTANT]
> **Fuori perimetro, segnalato e non corretto** (§ Fase 4): l'abstract di contesto si rigenera
> **prima** della stima e della conferma. Chi risponde "n" a `Proceed?` ha già pagato quella

### La tabella dei flag, vecchio → nuovo

| 4.5.0 | 4.6.0 | Ruolo |
| :- | :- | :- |
| `--translate [tag...]` | `--llm-translate [tag...]` | comando |
| `--retranslate <tag>...` | `--llm-retranslate <tag>...` | comando |
| `--context` | `--llm-context` | comando (combinabile con translate/retranslate: forza la rigenerazione) |
| `--context --show` | assorbito da `--llm-status` | — |
| `--llm-status` | `--llm-status` | comando |
| `--llm-status --ping` | `--llm-ping` | comando (status + una chiamata) |
| `--key set` / `status` / `clear` | `--llm-key-set` / `--llm-key-status` / `--llm-key-clear` | comando, gira da solo |
| `--dry-run` | `--llm-dry-run` | modificatore |
| `--force` | `--llm-auto` | modificatore |
| `--yes` | `--llm-noask` | modificatore |
| — | `--llm-debug` | modificatore |
| `--dryrun`, `--llmstatus` (refusi tollerati) | **nessuno** | spariscono: il namespace nuovo non ha refusi da tollerare |

Tutti i flag `--llm-*` restano **case-insensitive** (`--LLM-Translate` vale).

### Regole di combinazione (tutte errori, controllati prima di fare qualunque cosa)

Nell'ordine in cui vanno controllate — l'ordine decide quale messaggio vede chi sbaglia due cose:

1. nessun argomento che cominci (case-insensitive) per `--llm-` → **non è un comando LLM** (`null`).
2. un `--llm-*` fuori dal catalogo → `unknown flag "<flag>". LLM flags: <elenco>.`
3. un `--llm-*` insieme a `--add`/`-add`, `--status` o `--migrate` → errore. (Oggi `--translate --add fr-FR`
   ignora `--add` in silenzio: `maybeRunLlmCommand` esce prima.)
4. più di un `--llm-key-*`, oppure un `--llm-key-*` con qualunque altro `--llm-*` → errore.
5. `--llm-translate` insieme a `--llm-retranslate` → errore (oggi vince retranslate in silenzio).
6. `--llm-retranslate` senza tag → errore.
7. `--llm-status`/`--llm-ping` con translate, retranslate, context, dry-run, auto o noask → errore.
8. `--llm-dry-run` senza translate/retranslate/context → errore.
9. `--llm-auto` senza translate/retranslate → errore (il solo `--llm-context` non passa dai tetti).
10. `--llm-noask` senza translate/retranslate/context → errore (con context serve: soddisfa la guardia CI).
11. `--llm-debug` senza translate/retranslate/context/ping → errore (`--llm-status` da solo non chiama la rete:
    non ci sarebbe niente da tracciare).

`--fastverify` + qualunque `--llm-*` resta rifiutato in `cli.js` com'è oggi: basta che `hasAnyLlmFlag` cambi.

## Fase 1 — Implementazione

### 1.1 `lib/dev/llm/llmCommands.js` — il parser

Sostituisci `LLM_FLAGS`, `hasFlag` e `hasAnyLlmFlag` con un parser puro, **esportato** (i test lo chiamano
senza config):

```js
const LLM_PREFIX = "--llm-";

// Il catalogo completo. Tutto ciò che comincia per `--llm-` e non è qui è un errore: il prefisso
// è il namespace, e un refuso dentro il namespace non deve diventare una sync silenziosa.
const LLM_COMMANDS = [
  "--llm-translate", "--llm-retranslate", "--llm-context", "--llm-status", "--llm-ping",
  "--llm-key-set", "--llm-key-status", "--llm-key-clear",
];
const LLM_MODIFIERS = ["--llm-dry-run", "--llm-auto", "--llm-noask", "--llm-debug"];
const LLM_KNOWN = new Set([...LLM_COMMANDS, ...LLM_MODIFIERS]);
const KEY_ACTIONS = { "--llm-key-set": "set", "--llm-key-status": "status", "--llm-key-clear": "clear" };

/** Vero se `argv` contiene un qualunque `--llm-*`: usato anche da cli.js per il rifiuto
 *  `--fastverify` + comando esplicito. */
export function hasAnyLlmFlag(argv) {
  return argv.some((a) => a.toLowerCase().startsWith(LLM_PREFIX));
}

/**
 * Legge i flag LLM da `argv` e applica le regole di combinazione (doc/ImplementationPlans/4_6_0.md,
 * § "Regole di combinazione"). Pura: non legge config né disco.
 *
 * @returns {null | {
 *   translateTags: string[] | null, retranslateTags: string[] | null, context: boolean,
 *   status: boolean, ping: boolean, keyAction: "set" | "status" | "clear" | null,
 *   dryRun: boolean, auto: boolean, noAsk: boolean, debug: boolean,
 * }} `null` se non c'è nessun flag LLM.
 */
export function parseLlmArgs(argv) { … }
```

Dentro `parseLlmArgs`, passo per passo:

- `const low = argv.map((a) => a.toLowerCase());`
- `const llmArgs = low.filter((a) => a.startsWith(LLM_PREFIX));` — vuoto → `return null` (regola 1).
- regola 2: `const unknown = llmArgs.find((a) => !LLM_KNOWN.has(a));` → throw
  `[vitetranslate] unknown flag "${unknown}". LLM flags: ${[...LLM_KNOWN].join(", ")}.`
- regola 3: se `low` include `"--add"`, `"-add"`, `"--status"` o `"--migrate"` → throw
  `[vitetranslate] --llm-* flags cannot be combined with --add, --status or --migrate: run them separately.`
- `const has = (f) => low.includes(f);` e i booleani `translate`, `retranslate`, `context`, `status`, `ping`,
  `dryRun`, `auto`, `noAsk`, `debug`.
- regola 4: `const keyFlags = llmArgs.filter((a) => a in KEY_ACTIONS);` — `keyFlags.length > 1` → throw
  `[vitetranslate] pick one of --llm-key-set, --llm-key-status, --llm-key-clear.`;
  `keyFlags.length === 1 && llmArgs.length > 1` → throw `[vitetranslate] ${keyFlags[0]} runs alone.`
- regole 5–11 come da tabella, con questi messaggi esatti (i test li cercano per sottostringa):
  - 5: `--llm-translate and --llm-retranslate are alternatives: pick one.`
  - 6: `--llm-retranslate needs at least one language tag, e.g. --llm-retranslate fr-FR`
  - 7: `--llm-status and --llm-ping only combine with each other and with --llm-debug.`
  - 8: `--llm-dry-run only makes sense with --llm-translate, --llm-retranslate or --llm-context.`
  - 9: `--llm-auto only makes sense with --llm-translate or --llm-retranslate.`
  - 10: `--llm-noask only makes sense with --llm-translate, --llm-retranslate or --llm-context.`
  - 11: `--llm-debug only makes sense with --llm-translate, --llm-retranslate, --llm-context or --llm-ping.`
  Ogni messaggio comincia con `[vitetranslate] `.
- I tag: riusa `collectTagsAfter(argv, "--llm-translate")` / `"--llm-retranslate"` (già presente, già
  case-insensitive). `keyAction = keyFlags.length ? KEY_ACTIONS[keyFlags[0]] : null`.

### 1.2 `lib/dev/llm/llmCommands.js` — `maybeRunLlmCommand`

Riscrivi il corpo così (lo schema; i dettagli di stampa in § 1.7):

```js
export default async function maybeRunLlmCommand(argv, config) {
  const args = parseLlmArgs(argv);
  if (args === null) return false;

  if (args.keyAction) {
    await runKeyCommand(config, args.keyAction);
    return true;
  }

  const debug = args.debug ? createDebugTrace({ localeDir: localeDirOf(config) }) : null;
  debug?.write("run", { argv, cwd: process.cwd(), baseDir: config.baseDir, localeDir: config.localeDir,
    sourceLanguage: config.sourceLanguage, flags: args, llm: describeLlm(config) });

  try {
    if (args.status || args.ping) {
      await runLlmStatus(config, { ping: args.ping, debug });
      return true;
    }
    const result = await translatePass({
      config,
      tags: args.translateTags?.length ? args.translateTags : null,
      dryRun: args.dryRun, auto: args.auto, noAsk: args.noAsk,
      contextOnly: args.context && !args.translateTags && !args.retranslateTags,
      forceContext: args.context,
      retranslateTags: args.retranslateTags,
      debug,
    });
    reportOutcome(result); // § 1.7
    return true;
  } catch (error) {
    debug?.write("fatal-error", { message: error.message, stack: error.stack });
    throw error;
  } finally {
    if (debug?.dir) logEchoColored("llm", `debug trace: ${shortPath(debug.dir)} (${debug.count} file(s))`);
  }
}
```

- `describeLlm(config)`: `try { const llm = normalizeLlmOptions(config); … } catch (e) { return { invalid: e.message }; }`;
  restituisce `null` se non configurato, altrimenti `{ ...llm, driver: llm.driver ? "custom function" : "built-in openai-chat" }`.
  Niente chiave: `llm` non la contiene per costruzione (`connection.apiKey` non esiste).
- `shortPath` da `../vite/uty/shortPath.js`, come in `cli.js`.
- Il ramo `showContext` di `translatePass` **si elimina** (§ 1.5): il suo compito passa a `--llm-status`.
- `runKeyCommand(config, action)`: stessa funzione di oggi, cambiano solo i messaggi —
  `--key needs an \`llm.connection\`…` → `--llm-key-* needs an \`llm.connection\` configured (not \`llm.driver\`).`;
  il ramo `else` finale (azione sconosciuta) si toglie: il parser non lo può più produrre.

### 1.3 `lib/dev/llm/debugTrace.js` — nuovo file

Il registro di `--llm-debug`. Contratto:

```js
/** `2026-09-18 15:41:07` → `"260918154107"`: ordinabile per nome, ora locale. */
export function debugStamp(date) { … }

/**
 * @param {{ localeDir: string, now?: Date }} params
 * @returns {{
 *   write(label: string, data: string | object): void,
 *   setSecret(key: string | undefined): void,
 *   readonly dir: string | null,   // null finché non si è scritto niente
 *   readonly count: number,
 * }}
 */
export default function createDebugTrace({ localeDir, now = new Date() }) { … }

/** Le cartelle di trace esistenti, ordinate per nome (= per data). Mai un throw. */
export function listDebugTraces(localeDir) { … }
```

Comportamento, punto per punto:

1. **Cartella pigra.** Niente sul disco finché non arriva la prima `write`. Alla prima:
   `ensureContextDir(localeDir)` (da `contextFile.js`: così `.llm/.gitignore` nasce come sempre, se la
   cartella è nuova), poi `base = path.join(contextDir(localeDir), debugStamp(now))`; se esiste già prova
   `base-2`, `base-3`, … fino a una libera; `mkdirSync`; scrivi dentro un `.gitignore` con `*\n`.
   Quel `*` esclude da git la cartella intera, `.gitignore` compreso: **non si tocca** il `.llm/.gitignore`
   dell'utente (che per scelta della 4.5.0 non si riscrive mai dopo la nascita).
2. **Nome file**: `${String(n).padStart(3, "0")}-${label}.${ext}`, `n` da 1, incrementato **al momento
   della scrittura** (con la concorrenza l'ordine dei numeri è l'ordine degli eventi — è quello che si vuole).
   `label` ripulito: `label.replace(/[^A-Za-z0-9._-]/g, "_")`.
3. **Formato**: `data` stringa → `.txt` così com'è; oggetto → `.json` con
   `JSON.stringify(data, replacer, 2)`, dove `replacer` trasforma `Infinity` in `"Infinity"` (i preset
   `"unlimited"` del budget, altrimenti diventano `null`) e una `function` in `"[function]"`.
4. **Redazione**: il testo finale passa per `redact(text, secret)` di `apiKey.js` prima di toccare il disco.
   `setSecret(key)` si chiama appena la chiave è risolta (§ 1.5, § 1.6).
5. **Mai fatale**: ogni `write` è in `try/catch`. Al primo errore: una riga
   `logEchoColored("llm", \`debug trace: cannot write (${e.message}) — tracing off for this run\`, "warning")`,
   poi la trace si spegne (le `write` successive non fanno niente). Il run prosegue.
6. `listDebugTraces`: `readdirSync(contextDir(localeDir), { withFileTypes: true })`, tieni le cartelle il cui
   nome fa match con `/^\d{12}(-\d+)?$/`, ordina, restituisci i nomi. Cartella assente → `[]`.

Il file importa **solo** `fs`, `path`, `contextFile.js`, `apiKey.js`, `utility.js`: niente che finisca nel
bundle del plugin (`vitetranslate.js` importa `llmOptions.js` e basta — non cambiare questo).

### 1.4 Cosa si traccia: il catalogo delle etichette

| Etichetta | Formato | Chi la scrive | Contenuto |
| :- | :- | :- | :- |
| `run` | json | `maybeRunLlmCommand` | argv, cartelle, flag parsati, opzioni `llm` normalizzate (§ 1.2) |
| `api-key` | json | `translatePass`, `runLlmStatus` | `{ from }` — **mai** la chiave |
| `context-request` / `-response` / `-error` | json | `callModel` (§ 1.5) | la generazione dell'abstract |
| `context-result` | txt | `translatePass` | il `context.md` appena scritto, per intero |
| `estimate` | json | `translatePass` | tag, chiavi, richieste, `estimate`, `cost`, `ratios`, chiavi saltate per lingua, esito di `checkNumericCaps` |
| `confirm` | json | `translatePass` | `{ how: "noask" \| "costGuard" \| "prompt", ok, message? }` |
| `refused` | txt | `translatePass` | il messaggio di rifiuto (tetti, CI, TTY, declined) |
| `translate-<tag>-b<NN>-request` / `-response` / `-error` | json | `callModel` | un lotto; `NN` = indice del lotto **dentro quella lingua**, da 01 |
| `validate-<tag>-rejected` | json | `translatePass` | `[{ key, source, candidate, reason }]` del primo giro, se non vuoto |
| `validate-<tag>-unknown-keys` | json | `translatePass` | chiavi restituite dal modello e non richieste, se non vuoto |
| `repair-<tag>-b<NN>-request` / `-response` / `-error` | json | `callModel` | il giro di riparazione |
| `revalidate-<tag>-rejected` | json | `translatePass` | chi resta rifiutato dopo la riparazione |
| `ping-request` / `-response` / `-error` | json | `callModel` | `--llm-ping` |
| `summary` | json | `translatePass` | `perLanguageReport`, `filesWritten`, token misurati, costo, `stoppedOnBudget`, `durationMs` |
| `fatal-error` | json | `maybeRunLlmCommand` | `{ message, stack }` di un'eccezione che ferma il comando |

**Retry**: ogni tentativo ha i suoi file. Dal secondo in poi si inserisce `-a<N>` prima del tipo:
`translate-fr-FR-b01-a2-request`. Un `-error` porta sempre `{ attempt, message, status, retryAfter, willRetry }`.

Esempio di cartella dopo un `--llm-translate --llm-debug` con un 429 e un rifiuto del validatore:

```
locale/.llm/260918154107/
  .gitignore                              *
  001-run.json
  002-api-key.json
  003-estimate.json
  004-confirm.json
  005-translate-de-DE-b01-request.json
  006-translate-fr-FR-b01-request.json
  007-translate-fr-FR-b01-response.json
  008-translate-de-DE-b01-response.json
  009-translate-de-DE-b01-error.json      429, willRetry: true
  010-translate-de-DE-b01-a2-request.json
  011-translate-de-DE-b01-a2-response.json
  012-validate-fr-FR-rejected.json
  013-repair-fr-FR-b01-request.json
  014-repair-fr-FR-b01-response.json

```

(In questo esempio il 429 viene loggato come `-response` **e** come `-error`: la risposta grezza è la prova,
l'errore è la decisione di riprovare. Va bene così.)

### 1.5 `callModel.js`, `fetchDriver.js`, `translatePass.js`

**`fetchDriver.js`** — nuovo parametro opzionale `trace` (funzione `(kind, data) => void`, default
`undefined`):

- prima della `fetchImpl`: `trace?.("request", { url, method: "POST", body })` — `body` è l'oggetto
  esatto che si serializza (niente header: lì c'è la chiave).
- appena letto `text`, **prima** di controllare `response.ok`:
  `trace?.("response", { status: response.status, statusText: response.statusText, elapsedMs, headers: Object.fromEntries(response.headers), body: tryParseJson(text) })`
  dove `tryParseJson` restituisce l'oggetto o, se non è JSON, la stringa. `elapsedMs` = `Date.now()` prima
  e dopo la `fetchImpl`. Nei test i `Response` finti potrebbero non avere `headers` iterabili: usa
  `response.headers ? Object.fromEntries(response.headers) : {}` dentro un `try`.
- Nient'altro cambia.

**`callModel.js`**:

- `callModel` accetta due parametri in più: `debug` (la trace o `null`) e `label` (stringa, default
  `mode === "context" ? "context" : "translate"`).
- `withRetry(attempt, { …, onAttemptError })`: `attempt` riceve il numero del tentativo
  (`attempt(tryNum)`, da 0), e nel `catch` si chiama `onAttemptError?.(error, tryNum, willRetry)` prima di
  decidere se rilanciare o dormire. `willRetry = retryable && tryNum < maxRetries`.
- Dentro `callModel`:

```js
const labelFor = (tryNum) => (tryNum === 0 ? label : `${label}-a${tryNum + 1}`);
const attempt = async (tryNum) => {
  const l = labelFor(tryNum);
  const trace = debug ? (kind, data) => debug.write(`${l}-${kind}`, data) : undefined;
  let raw;
  if (driver) {
    trace?.("request", { mode, systemPrompt, userPayload: tryParseJson(userPayload) });
    raw = await driver({ connection, apiKey, systemPrompt, userPayload, mode });
    trace?.("response", raw);
  } else {
    raw = await fetchDriver({ connection, apiKey, systemPrompt, userPayload, mode, trace });
  }
  …normalizzazione di oggi…
};
const onAttemptError = debug
  ? (error, tryNum, willRetry) => debug.write(`${labelFor(tryNum)}-error`, {
      attempt: tryNum + 1, message: error.message, status: error.status, retryAfter: error.retryAfter, willRetry,
    })
  : undefined;
```

  Metti `tryParseJson` in `callModel.js` ed esportalo; `fetchDriver.js` lo importa da lì? **No**: creerebbe
  un import circolare (`callModel` importa `fetchDriver`). Mettilo in `debugTrace.js` ed esportalo da lì;
  lo importano entrambi.

**`translatePass.js`**:

**`llmOptions.js`**:

### 1.7 Esiti a schermo e codice d'uscita — il bug della 4.5.0

Oggi `maybeRunLlmCommand` scarta il risultato di `translatePass`: un rifiuto dei tetti, della guardia CI o
della conferma non stampa niente ed esce con 0. Nuova funzione in `llmCommands.js`:

```js
function reportOutcome(result) {
  if (result.mode === "refused") {
    printRefusal(result.message);          // llmReport.js, esiste già ed è inutilizzata
    if (!result.declined) process.exitCode = 1;
  } else if (result.mode === "nothing-to-do") {
    logEchoColored("llm", "nothing to translate: every target language is complete.");
  } else if (result.mode === "context") {
    logEchoColored("llm", result.regenerated ? "context abstract regenerated." : "context abstract left as it is.");
  }
}
```

- "declined" (l'utente ha risposto no) non è un fallimento: exit 0. Ogni altro rifiuto: exit 1 — è quello
  che serve a una CI per accorgersi che non ha tradotto niente.
- `mode: "context"` con `regenerated: false` succede con `context.mode: "off"` o con un file scritto a mano:
  in quel caso aggiungi il motivo se `translatePass` lo sa (`reason: "off"` / `"unmanaged"` nel return) —
  una riga, niente di più.

### 1.8 `--llm-status` assorbe l'abstract; `--llm-ping`

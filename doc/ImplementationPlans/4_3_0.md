## Il problema, in concreto

Questo file:

```jsx
export default function Pippolo() {
 return (<p>_%_samoro_%_</p>)
}
```

esce dal transform così, e nessuno protesta:

```jsx
export default function Pippolo() {
 return (<p>{"_<_Pippolo_iq72iv_/_samoro_>_"}</p>)
}
```

A schermo l'utente finale legge `_<_Pippolo_iq72iv_/_samoro_>_`. In build, dove
`includeFallback` è `false`, legge `_<_Pippolo_iq72iv_>_`: si perde perfino la parola.

Tre cose vanno capite prima di toccare il codice.

1. **Il marcatore è scritto benissimo.** L'avviso `malformed marker` non scatta, perché quello
   controlla che il marcatore apra *e* chiuda l'intera stringa, ed è così.
2. **La chiave entra comunque nelle tabelle.** `registerMarker` viene chiamato prima di
   qualunque decisione sulla riscrittura, quindi `Pippolo_iq72iv: samoro` finisce nei file di
   lingua e il traduttore la traduce. La traduzione esiste, nel chunk giusto, e nessuno la
   legge.
3. **Il runtime non può accorgersene.** Quella stringa è un figlio di testo di un elemento
   host: non passa da nessun componente, e non esiste in React un punto in cui intercettarla.
   Tutto `errorSolve` — `‼️`, `🔸`, `🔹` — vive dentro `Translate` e `ts()`.

È l'unica delle tre posizioni riconosciute (`StringLiteral`, `JSXText`, `TemplateElement`) in
cui un marcatore compilato può raggiungere lo schermo senza passare da un componente.

## Perché l'espressione e non l'attributo

Il marcatore va emesso come `t={"..."}`. **Mai** come `t="..."`. Un attributo JSX in forma di
stringa non è una stringa JS, e le due differenze non sono teoriche — misurate sul parser:

| Fallback | `t="..."` | `t={"..."}` |
|---|---|---|
| `dice "ciao"` | **PARSE ERROR**, la build muore | `dice "ciao"` |
| `Tom &amp; Jerry` | `Tom & Jerry`, ridecodificato in silenzio | `Tom &amp; Jerry` |

Il secondo è il peggiore dei due: non fallisce, e il fallback incorporato smette di
corrispondere al testo che sta in tabella.

È la stessa ragione, già scritta nel commento sopra il ramo `parent?.type === "JSXAttribute"`
di `extractMarkers.js`, per cui i valori di attributo sono **già oggi** avvolti in
un'espressione. Si riusa `jsString()`, la funzione che c'è già in quel file: fa
`JSON.stringify` più l'escape di U+2028 e U+2029.

## La regola del genitore host

**Si avvolge solo quando il genitore del `JSXText` è un elemento host o un fragment.**

Il motivo è il tipo di `props.children` del genitore. Compilato da `preset-react`:

```js
// oggi                    -> children è una STRINGA
_jsx("p", { children: "_<_k_>_" })
// avvolto                 -> children è un ELEMENTO
_jsx("p", { children: _jsx(__vtTranslate, { t: "_<_k_>_" }) })
```

Sotto `<p>` è indifferente, un elemento host rende qualunque nodo. Sotto un componente altrui
no: un `<MyButton>_%_Salva_%_</MyButton>` che internamente fa `children.toUpperCase()` oggi
riceve una stringa e con l'auto-wrap riceverebbe un oggetto.

**Il guadagno collaterale è che questa regola assorbe da sola il doppio wrapping.** `Translate`
è un componente, quindi `<Translate>_%_a_%_</Translate>` non viene mai toccato per costruzione:
non serve tracciare i binding importati, né confrontare il nome del genitore con una lista.

Come si decide, alla lettera. Il genitore è host se e solo se:

- `parent.type === "JSXFragment"`, **oppure**
- `parent.type === "JSXElement"` **e** `parent.openingElement.name.type === "JSXIdentifier"`
  **e** `/^[a-z]/.test(parent.openingElement.name.name)`.

Tutto il resto — `JSXMemberExpression` (`<Foo.Bar>`), `JSXNamespacedName` (`<svg:rect>`),
qualunque identificatore che non comincia con una minuscola ASCII — **non è host** e non si
avvolge. È deliberatamente conservativo: nel dubbio si lascia il comportamento di oggi.

Il `parent` è già disponibile nel visitor: `walk()` lo passa, e per i figli di un array passa
il nodo che conteneva l'array, quindi per un `JSXText` il `parent` è già il `JSXElement`.
Verificalo leggendo `walk()` prima di scrivere, non fidarti di questa riga.

## Fase 1 — Implementazione

### 1.1 `lib/dev/babel/extractMarkers.js` — la firma

Aggiungi `autoWrap = false` alla destrutturazione delle opzioni, accanto a `rewrite` e
`includeFallback`, e documentalo nel JSDoc con la stessa forma degli altri:

```js
 * @param {boolean} [options.autoWrap=false] - avvolge in <Translate t={...} /> il JSXText
 *   interamente marcato il cui genitore è un elemento host. Vedi doc/ImplementationPlans/4_3_0.md.
```

### 1.2 L'alias, deciso una volta per file

Prima del `walk`, non dentro:

```js
// L'alias è un identificatore che il transform inietta nel file dell'utente: se per caso
// esiste già, ombreggerebbe il suo. La ricerca è per SOTTOSTRINGA e non per identificatore
// vero, ed è eccessiva apposta — costa una scansione lineare su un file che stiamo già
// leggendo per intero, e sbagliarla costa un binding rubato in silenzio.
let alias = "__vtTranslate";
if (autoWrap && rewrite) {
  let n = 1;
  while (code.includes(alias)) alias = `__vtTranslate${++n}`;
}
```

### 1.3 Il ramo `JSXText` del visitor

Sostituisci il solo ramo `type === "JSXText"`. Il resto del visitor non si tocca.

```js
} else if (type === "JSXText") {
  const nl = "\n".repeat(countNewlines(code, node.start, node.end));
  if (autoWrap && isHostParent(parent)) {
    // Gli spazi a cavallo del nodo: JSX tiene una corsa di spazi che NON contiene un a-capo
    // e scarta quella che lo contiene. Oggi lo splice rimette in coda gli a-capo e quindi
    // perde lo spazio significativo; qui lo si rimette come `{" "}`, che è la forma che
    // sopravvive a qualunque genitore.
    const raw = code.slice(node.start, node.end);
    const lead = /^\s+/.exec(raw)?.[0] ?? "";
    const tail = raw.length > lead.length ? (/\s+$/.exec(raw)?.[0] ?? "") : "";
    const pre = lead !== "" && !lead.includes("\n") ? '{" "}' : "";
    const post = tail !== "" && !tail.includes("\n") ? '{" "}' : "";
    text = `${pre}<${alias} t={${jsString(value)}} />${post}${nl}`;
    wrapped = true;
    // Un testo auto-avvolto non può ricevere argomenti: il tag è autochiuso e `a` non c'è.
    // Ogni %s renderà il mark `absentDataInArray` (⁇ di default), che a schermo si scopre
    // molto dopo. Categoria a sé perché printWarnings le elenca per esteso.
    if (value.includes(PLACEHOLDER)) {
      (warn ?? defaultWarn)(
        `auto-wrapped text with a "%s" placeholder in ${colorize("nome", `"${relPathOf(filename, baseDir)}"`)}: ` +
        `"${cita(inner)}" cannot receive arguments — write <Translate t={["${SOURCE_OPEN}...${SOURCE_CLOSE}", value]} /> instead.`,
        "autowrap-placeholder"
      );
    }
  } else {
    text = `{${jsString(value)}}${nl}`;
  }
}
```

Note per chi implementa, tutte necessarie:

- `PLACEHOLDER` va importato da `../../markerSyntax.js`, accanto a `compiledMarker` e
  `SOURCE_OPEN` che ci sono già.
- `cita` e `colorize` e `relPathOf` e `defaultWarn` sono già importati o definiti nel file.
- `wrapped` è una variabile dichiarata accanto a `edits`, inizializzata a `false`.
- `nl` va calcolato **prima** del ramo e usato in entrambi: è la logica esistente, non toccarla.
- `isHostParent` è una funzione di modulo, sotto `jsString`, che implementa alla lettera il §
  "La regola del genitore host". Non inline: va testata da sé.
- La `else` deve restare **byte per byte** quella di oggi. Se `autoWrap` è `false` l'uscita
  dell'estrazione non cambia di un carattere, ed è l'invariante 1.

### 1.4 L'import appeso in fondo

Dopo il `walk` e prima dello `splice`:

```js
// In FONDO, non in testa. Gli import ESM sono hoisted, quindi la posizione non conta per il
// significato; conta eccome per tutto il resto. Appeso in coda, nessuna riga preesistente si
// sposta: la nostra sourcemap resta l'identità, il `lineNumber` che il plugin React incide in
// ogni jsxDEV resta giusto, gli stack di errore restano giusti, e una direttiva "use client"
// resta il primo statement del file. In testa costerebbe tutto questo per niente.
const tail = wrapped
  ? `${code.endsWith("\n") ? "" : "\n"}import { Translate as ${alias} } from "@sepoina/vitetranslate/react";\n`
  : "";
```

La condizione di uscita anticipata **non cambia**: resta `if (!rewrite || edits.length === 0)
return null;`. Senza edit non ci può essere stato un wrap, quindi `tail` è già `""`.

Il ramo `code.endsWith("\n")` non è cosmetico: senza, l'import si attaccherebbe in coda
all'ultima riga di codice se il file non finisce con un a-capo, che è un file valido e
frequente. Con il ramo, la riga aggiunta è sempre e solo una.

### 1.5 `splice()` deve conoscere la coda

Cambia la firma in `splice(code, edits, filename, sourceMaps, tail)` e, subito dopo il
`copy(code.slice(cursor))` finale:

```js
  // La coda mappa sull'ultima riga sorgente: `limit` uguale a `srcLine` impedisce a `copy` di
  // far avanzare la riga sorgente sugli a-capo che stiamo aggiungendo noi. Senza, le righe
  // dell'import punterebbero oltre la fine del sorgente.
  if (tail) copy(tail, srcLine);
```

Passa `tail` dalla `return splice(...)` in fondo a `extractMarkers`.

### 1.6 `lib/dev/vite/vitetranslate.js` — l'opzione

**Non riusare `leggiFlag`.** Quello è scritto per opzioni con default `true` e restituisce
`defs[chiave] !== false`, cioè considera acceso qualunque valore non-`false`: su un default
`false` accenderebbe la funzione a chi ha scritto `autoWrap: 0`. Serve il duale:

```js
// Stessa lettura case-insensitive di simpleLog e delle due autoSync, per la stessa ragione:
// "autowrap" o "AutoWrap" non producono nessun errore e resterebbero silenziosamente al
// default. Il duale di leggiFlag: qui il default è spento, quindi si accende solo su `true`
// esplicito, non su qualunque valore non-false.
const autoWrapKey = Object.keys(defs).find((k) => k.toLowerCase() === "autowrap");
const autoWrap = autoWrapKey !== undefined && defs[autoWrapKey] === true;
```

Poi, nella chiamata a `extractMarkers` dentro `transform.handler`, aggiungi `autoWrap,` alla
lista di opzioni. Nient'altro cambia in questo file.

### 1.7 `lib/index.d.ts`

In `VitetranslateOptions`, dopo `includeFallback`:

```ts
  /**
   * Avvolge automaticamente in `<Translate>` il testo JSX interamente marcato che si trova
   * dentro un elemento HTML. Senza, un `<p>_%_ciao_%_</p>` a cui manca il `<Translate>`
   * stampa a schermo il marcatore compilato. Non tocca gli attributi, che restano a `ts()`,
   * né il testo dentro un componente. Default: `false`.
   */
  autoWrap?: boolean;
```

### 1.8 `test/list/babelTranslateReference.mjs`

L'implementazione di riferimento è **l'unica prova indipendente che l'estrazione veloce sia
corretta** (leggi il commento in testa a quel file). Se non impara a fare la stessa cosa, il
corpus dell'auto-wrap non ha con cosa essere confrontato.

Va toccata il minimo indispensabile:

- l'opzione `autoWrap` si legge da `options`, come `includeFallback`;
- nel ramo `JSXText`, quando `autoWrap` è acceso e il genitore è host (`p.parent`), si usa
  `p.replaceWithMultiple([...])` invece di `p.replaceWith(...)`, costruendo l'elemento JSX
  autochiuso con `t.jsxElement(t.jsxOpeningElement(t.jsxIdentifier(alias), [attr], true), null, [], true)`;
- l'import si aggiunge in `Program.exit` con un `path.pushContainer("body", ...)`, che lo mette
  in fondo come fa lo splice;
- gli spazi `{" "}` **non** servono qui: il test di parità normalizza attraverso `preset-react`,
  e un `{" "}` e un `JSXText` di un solo spazio compilano entrambi a `" "`.

Se questo punto si rivela più costoso di quanto scritto qui, **è un ask**, non una decisione:
l'alternativa è escludere i casi auto-wrap dal corpus di parità, e va autorizzata.

### 1.9 Cosa NON fare in fase 1

- Non toccare `lib/react/`. Nessun file, nessuna riga.
- Non toccare `registerMarker`, `markerCore.js`, `markerSyntax.js`. Gli id non cambiano.
- Non passare `autoWrap` da `scanSource.js`: la scansione di sync gira con `rewrite: false` e
  non emette codice. Se lo passi, non succede niente, ed è peggio: sembra che serva.
- Non correggere lo spazio perso sul percorso **non** avvolto. È un difetto reale e
  preesistente, ma correggerlo cambia l'uscita di default e fa cadere l'invariante 1. Resta
  fuori da questo piano di proposito.
- Non introdurre una seconda forma di marcatore (chiave e fallback come prop separate). Il
  marcatore compilato resta l'unico contratto fra compilatore e runtime, ed è la ragione per
  cui `markerSyntax.js` esiste.

| T21 | lo stesso con `autoWrap: false` | nessun avviso nuovo |

**Opzione del plugin** (dove stanno già i test delle altre opzioni):

| # | Caso | Atteso |
|---|---|---|
| T22 | `autoWrap: true` / `autowrap: true` / `AutoWrap: true` | tutte e tre accendono |

**Facoltativo, se il costo è ragionevole** — il test che chiude davvero il cerchio: prendere
l'uscita del transform con `autoWrap: true`, compilarla con `preset-react`, e renderla in SSR
contro una tabella compilata, come fa `test/list/translateComponent.test.mjs`. Deve uscire il
testo tradotto, non l'opcode. Se il montaggio del modulo virtuale rende il test fragile,
appuntalo come non fatto invece di forzarlo.

Alla fine della fase: `node test/run.mjs` deve dare **almeno** 36/36 test e più di 1248
asserzioni. Un test preesistente che cambia esito **non è un test da aggiornare: è una

## Invarianti da NON rompere in questo piano

Tutte verificabili. Se una cade, ci si ferma e si passa alla fase 4.

1. **Con `autoWrap` spento, l'uscita di `extractMarkers` è byte-identica alla 4.2.4** per
   qualunque ingresso. È l'invariante che rende tutto il piano additivo, e la verificano i test
   preesistenti passando senza essere toccati.
2. **`lib/react/` non cambia**, quindi `lib/dist/react.es.js` e `lib/dist/react.cjs` restano
   byte-identici e `npm run estimateSize` resta a 4.169 B gzip.
3. **Gli id non cambiano e le tabelle non cambiano forma.** `registerMarker` non si tocca,
   nessun file di lingua va risincronizzato per effetto di questo piano.
4. **Nessuna riga preesistente del file trasformato si sposta.** L'uscita ha al massimo una riga
   in più, in coda.
5. **Il marcatore compilato resta l'unico contratto** fra estrazione e runtime. Niente chiave
   passata come prop separata, niente seconda forma da tenere in sync con `markerSyntax.js`.
6. **`rewrite: false` non avvolge mai** e non appende mai un import.
7. **Nessuna firma pubblica cambia.** `autoWrap` è additiva e facoltativa; `lib/index.js` e
   `lib/react/index.js` esportano gli stessi nomi.

## Cosa questo piano NON fa, di proposito

- **Non tocca gli attributi.** `title="_%_x_%_"` continua a richiedere `ts()`: un componente non
  rende dentro una prop, e un hook non si inietta.
- **Non corregge lo spazio perso sul percorso non avvolto.** Cambierebbe l'uscita di default.
  Candidato a un piano suo.
- **Non introduce un componente dedicato.** Sarebbe più snello del `Translate` generale, che
  porta l'arbitraggio fra `o`, `t` e `children` di cui un punto di chiamata generato dal
  compilatore non ha bisogno. Costa byte nel runtime browser, che è la cosa che questo piano
  promette di non muovere.
- **Non accende `autoWrap` di default.** È un candidato per la 5.0, dopo che la funzione ha
  girato su progetti veri.
- **Non fa niente per il markup nel testo JSX.** `<p>_%_ciao <b>mondo</b>_%_</p>` è spezzato dal
  parser JSX prima che l'estrazione lo veda, e resta la forma a stringa. Si documenta, non si
  risolve.

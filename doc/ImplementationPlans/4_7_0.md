# Piano di implementazione 4.7.0 — Delimitatori configurabili e nomi brevi

> [!NOTE]
> **Per il revisore umano**
> - **Delimitatori configurabili**: `marker` (uno per entrambi i capi) oppure `markerStart`/`markerEnd`, e vince lo specifico. Il default resta `_%_`. Validati alla costruzione del plugin; le chiavi non cambiano, perché l'hash si calcola sul testo interno.
> - **L'opzione arriva a tutti i lettori**: estrazione, i tre pre-filtri, le cache (`scan.json`, `markers.json`), il runtime (modulo virtuale) e l'estensione, che la legge dalla sonda di vite.config e altrimenti usa `_%_`.

> - **Estensione**: evidenziazione e Results seguono i delimitatori del progetto e i nomi brevi. `IDE_API` resta 1, quindi nessun vincolo d'ordine fra npm e .vsix.
> - **Demo nuova** `demo/Vite_8/customMarkers` con `≼…≽` (U+227C, U+227D: Unicode rarissimi). Le frasi stanno fra i tag senza `<Trans>` (`autoWrap: true`, stesse chiavi); resta solo `<Trans t={nota} />` per la lista di dati.

## Il concetto (leggilo prima di scrivere codice)

### Prima e dopo, su un esempio

```js
// vite.config.js
vitetranslate({ localeDir: "locale", sourceLanguage: "it-IT", markerStart: "≼", markerEnd: "≽" })
```

```jsx
import { Trans, useTrans } from "@sepoina/vitetranslate/react";

const steps = ["≼Scegli≽", "≼Paga≽"];        // stessa chiave che aveva "_%_Scegli_%_"
<Trans t={steps[0]} />
<Trans>Ciao <b>{nome}</b></Trans>                    // la macro non ha bisogno di delimitatori
const trans = useTrans();
<input placeholder={trans`Cerca`} title={trans("≼Filtra≽")} />
```

La chiave è `Basename_hash(testo interno, percorso relativo)` (`registerMarker` in `lib/dev/babel/markerCore.js`): né il
delimitatore né il nome del componente ci entrano. Quindi rinominare `<Translate>` in `<Trans>`, `ts` in `trans`, o riscrivere `_%_…_%_` in
`≼…≽`, **non cambia nessuna chiave e nessuna traduzione**. Fanno eccezione i testi che *contengono* la parola `<Translate>` (un sito
che parla della libreria): quelli cambiano messaggio, e vanno ritradotti (Fase 5).

### Chi legge i delimitatori, e come li riceve

| Lettore | Da dove arrivano i delimitatori |
| :- | :- |
| Transform di Vite (`vitetranslate.js`) | `resolveMarkers(defs)` alla costruzione → filtro del transform, `mayHaveMarkers`, `extractMarkers({ markers })` |
| Sync del CLI (`syncCore` → `scanSource`) | `loadConfig()` → `config.markers` → `service.markers` |
| Auto-sync (`autoSync.js`) | `config.markers` → `fastVerify({ expect: { …, markers } })` |
| `fastVerify` del CLI (`--fastverify`, non legge vite.config) | `record.markers` in `scan.json`; un vite.config cambiato invalida già il record (firma del file) |
| Indice delle voci (`markers.json`) | campo `markers`, confrontato da chi lo legge |
| Runtime nel browser | `markerStart`/`markerEnd` del modulo virtuale (percorsi di degrado e messaggi di sviluppo) |
| Estensione, Results | sonda → `vitetranslate.markers` → `input.markers` → `scan()` → `mayHaveMarkers`/`extractMarkers` della libreria del progetto |
| Estensione, evidenziazione | `ProjectMarkers` (nuovo) → la lettura della sonda per il progetto che contiene il file |

La **forma** dei delimitatori, fra un lettore e l'altro, è sempre l'oggetto semplice `{ start, end }` (serializzabile: passa dalla
sonda). Dentro un lettore si trasforma in una *sintassi* con `markerSyntaxOf(start, end)` (Blocco A), che risponde alle domande che
oggi si fanno a mano con `startsWith(SOURCE_OPEN)`.

### Glossario del piano

- **delimitatori / marcatori**: la coppia `{ start, end }`. "Di serie" = `_%_`/`_%_`.
- **sintassi** (`m`): l'oggetto di `markerSyntaxOf`: `start`, `end`, `min`, `isDefault`, `wraps(s)`, `inner(s)`, `stray(s)`.
- **marcatore vecchio**: un `_%_` in un progetto che usa altri delimitatori.
- **nomi brevi / nomi estesi**: `Trans`, `useTrans`, `TransContainer`, `useTransLanguage` / `Translate`, `useTranslateToString`,
  `TranslateContainer`, `useTranslateLanguage`.

## Verifiche fatte durante il piano

- **Gli alias funzionano già nella 4.6.4** (`import { Translate as Trans }`): `macroForms.js` raccoglie i nomi locali degli import,
  `macroNames` dell'estensione legge gli `as`. Gli export nuovi tolgono solo l'`as`.
- **Offset di Babel** (verificati eseguendo `@babel/core` del repo): un `TemplateElement` copre il solo testo grezzo (senza backtick
  né `${`); uno `StringLiteral` comprende le virgolette; un `JSXText` comprende gli spazi e gli a-capo ai bordi.
- **L'algoritmo di riscrittura dell'Appendice B** è stato eseguito nello scratchpad su 10 casi: stringhe con apostrofo escapato,
  template con e senza `${}`, attributo JSX, frase spezzata da un tag su righe CRLF (CRLF conservato), `<Trans>_%_…_%_</Trans>`,
  `{"_%_…_%_"}`, commento e `import` lasciati intatti, stringa con `_%_` in mezzo lasciata intatta, ritorno `≼…≽` → `_%_…_%_`,
  passaggio a un delimitatore unico (`§`). Il controllo sulle chiavi (che richiede l'estrazione con delimitatori personalizzati)
  **non** è stato eseguito: lo prova la Fase 2.
- `README.md` oggi misura **10 212 byte** (tetto 10 000, tolleranza 10%): la Fase 5 non deve superare 11 000.

```js
/** I delimitatori di serie, nella forma in cui viaggiano fra un lettore e l'altro (4.7.0). */
export const DEFAULT_MARKERS = { start: SOURCE_OPEN, end: SOURCE_CLOSE };

/**
 * La sintassi del marcatore sorgente per una coppia di delimitatori (4.7.0): le domande che
 * estrazione, evidenziazione e riscrittura fanno a un testo. Senza argomenti, quella di serie.
 * Nessuna istanza a livello di modulo: il runtime non la importa, e non deve trovarsela in bundle.
 *
 * @param {string} [start]
 * @param {string} [end]
 */
export function markerSyntaxOf(start = SOURCE_OPEN, end = SOURCE_CLOSE) {
  const min = start.length + end.length;
  return {
    start,
    end,
    /** Il marcatore vuoto: sotto questa lunghezza un delimitatore aprirebbe e chiuderebbe se stesso. */
    min,
    isDefault: start === SOURCE_OPEN && end === SOURCE_CLOSE,
    /** Il testo è avvolto per intero? */
    wraps: (s) => s.length >= min && s.startsWith(start) && s.endsWith(end),
    /** Il contenuto senza i delimitatori; solo su un testo per cui `wraps` è vero. */
    inner: (s) => s.slice(start.length, s.length - end.length),
    /** Contiene un delimitatore, d'apertura o di chiusura? */
    stray: (s) => s.includes(start) || (end !== start && s.includes(end)),
  };
}

/**
 * Il file può contenere qualcosa da estrarre? Un pre-scarto: il parse decide.
 *
 * @param {string} code
 * @param {{ start: string, end: string }} [markers] - i delimitatori del progetto; default `_%_`.
 *   Con delimitatori diversi passa anche un file con `_%_`: l'estrazione ci deve arrivare per dare
 *   l'avviso dei marcatori vecchi.
 */
export function mayHaveMarkers(code, markers) {
  const start = markers?.start ?? SOURCE_OPEN;
  return code.includes(start) ||
    (start !== SOURCE_OPEN && code.includes(SOURCE_OPEN)) ||
    (code.includes(RUNTIME_IMPORT) && MACRO_IMPORT_RE.test(code));
}
```

### A.2 `lib/dev/vite/uty/markerOptions.js`

```js
// Architettura d'insieme: doc/structure.md § "Fase 0 — Autoring: il marcatore".
// Quel documento è la fonte di verità sul funzionamento della libreria: se cambi il
// comportamento di questo file, aggiornalo nello stesso commit.
//
// I delimitatori del progetto (4.7.0): `marker`, `markerStart`, `markerEnd`, controllati alla
// costruzione del plugin come `localeDir`. Due lettori: il plugin (vitetranslate.js) e il comando di
// riscrittura (rewriteMarkers.js), che controlla con le stesse regole i delimitatori di partenza.

import { SOURCE_OPEN, SOURCE_CLOSE, PLACEHOLDER } from "../../../markerSyntax.js";

// Ognuno ha già un significato in uno dei posti dove un marcatore può stare:
//   < > { }  JSX, i tag del dialetto, gli slot <0>, gli argomenti ICU
//   " ' `    chiuderebbero la stringa o il template che lo contiene
//   \        un escape: il testo scritto non sarebbe quello letto
//   &        un'entità HTML nel testo JSX
const VIETATI = ["<", ">", "{", "}", '"', "'", "`", "\\", "&"];

/**
 * Cosa non va in un delimitatore, o null.
 * @param {unknown} value
 * @param {string} name - il nome dell'opzione, per il messaggio
 * @returns {string | null}
 */
export function markerProblem(value, name) {
  if (typeof value !== "string" || value === "") {
    return `${name} must be a non-empty string (got ${typeof value === "string" ? '""' : String(value)})`;
  }
  const q = JSON.stringify(value);
  if (/\s/u.test(value)) return `${name} ${q} contains whitespace: JSX trims and folds it, so the marker would never match`;
  if (/[\u0000-\u001f\u007f]/.test(value)) return `${name} ${q} contains a control character`;
  const c = VIETATI.find((ch) => value.includes(ch));
  if (c) return `${name} ${q} contains ${JSON.stringify(c)}, which already means something in JSX, strings or messages (not allowed: < > { } " ' \` \\ &)`;
  if (value.includes(PLACEHOLDER)) return `${name} ${q} contains "${PLACEHOLDER}", the placeholder`;
  return null;
}

/** Cosa non va nella coppia, o null: due delimitatori diversi non devono contenersi a vicenda. */
export function markerPairProblem(start, end) {
  if (start === end || (!start.includes(end) && !end.includes(start))) return null;
  return `markerStart ${JSON.stringify(start)} and markerEnd ${JSON.stringify(end)} overlap: one contains the other, ` +
    `so a closing marker would also read as an opening one. Pick two that don't, or the same one twice (marker)`;
}

// Le chiavi cercate senza badare a maiuscole, come autoWrap: "markerstart" vale "markerStart".
function leggi(defs, nome) {
  const k = Object.keys(defs ?? {}).find((x) => x.toLowerCase() === nome.toLowerCase());
  return k === undefined ? undefined : defs[k];
}

/**
 * I delimitatori dalle opzioni del plugin. Vince lo specifico: `markerStart ?? marker ?? "_%_"`.
 * @returns {{ start: string, end: string }}
 * @throws {Error} con tutti i problemi trovati, uno per riga
 */
export function resolveMarkers(defs) {
  const marker = leggi(defs, "marker");
  const ms = leggi(defs, "markerStart");
  const me = leggi(defs, "markerEnd");
  const problemi = [];
  for (const [nome, v] of [["marker", marker], ["markerStart", ms], ["markerEnd", me]]) {
    if (v === undefined) continue;
    const p = markerProblem(v, nome);
    if (p) problemi.push(p);
  }
  if (problemi.length === 0) {
    const coppia = markerPairProblem(ms ?? marker ?? SOURCE_OPEN, me ?? marker ?? SOURCE_CLOSE);
    if (coppia) problemi.push(coppia);
  }
  if (problemi.length) throw new Error(`invalid marker option:\n  - ${problemi.join("\n  - ")}`);
  return { start: ms ?? marker ?? SOURCE_OPEN, end: me ?? marker ?? SOURCE_CLOSE };
}
```

### B.1 `planRewrite` (verificato nello scratchpad, salvo `parseSource` e la visita, presi da extractMarkers.js)

```js
import { markerSyntaxOf } from "../../../markerSyntax.js";
import { parseSource } from "../../babel/extractMarkers.js";

// Gli spazi che JSX toglie ai bordi di un testo: non `trim()`, che toglierebbe anche un U+00A0
// scritto letterale, che per JSX è testo.
const BORDI = /^[ \t\r\n]+|[ \t\r\n]+$/g;
const SORGENTI_DI_MODULO = new Set(["ImportDeclaration", "ExportNamedDeclaration", "ExportAllDeclaration"]);

// Visita generica guidata dalle VISITOR_KEYS, col genitore.
function visita(n, genitore, keys, fn) {
  if (!n || typeof n.type !== "string") return;
  fn(n, genitore);
  for (const k of keys?.[n.type] ?? Object.keys(n)) {
    if (k === "loc" || k.endsWith("Comments")) continue;
    const v = n[k];
    if (Array.isArray(v)) for (const c of v) visita(c, n, keys, fn);
    else if (v && typeof v === "object") visita(v, n, keys, fn);
  }
}

/**
 * Il codice di un file con i marcatori `from` riscritti in `to`. Pura: nessun disco. Riscrive solo i
 * delimitatori, mai il testo; un marcatore che l'estrazione non riconoscerebbe può restare com'è o
 * cambiare: lo dice il confronto delle chiavi, che è il vero controllo.
 *
 * @returns {{ code: string, count: number }} count = marcatori riscritti (una coppia = 1)
 */
export function planRewrite(code, filename, from, to) {
  const { ast, visitorKeys } = parseSource(code, filename);
  const f = markerSyntaxOf(from.start, from.end);
  const edits = []; // [inizio, fine, testo nuovo]
  let count = 0;
  const apri = (pos) => edits.push([pos, pos + f.start.length, to.start]);
  const chiudi = (pos) => edits.push([pos - f.end.length, pos, to.end]);

  visita(ast.program, null, visitorKeys, (node, genitore) => {
    if (node.type === "StringLiteral") {
      if (SORGENTI_DI_MODULO.has(genitore?.type)) return;
      const raw = code.slice(node.start + 1, node.end - 1); // senza virgolette, escape compresi
      if (f.wraps(raw)) { apri(node.start + 1); chiudi(node.end - 1); count++; }
    } else if (node.type === "TemplateLiteral") {
      // Gli offset di un TemplateElement coprono il solo testo grezzo (verificato).
      const primo = node.quasis[0];
      const ultimo = node.quasis[node.quasis.length - 1];
      const a = code.slice(primo.start, primo.end);
      const z = code.slice(ultimo.start, ultimo.end);
      if (node.quasis.length === 1 ? f.wraps(a) : a.startsWith(f.start) && z.endsWith(f.end)) {
        apri(primo.start); chiudi(ultimo.end); count++;
      }
    } else if (node.type === "JSXElement" || node.type === "JSXFragment") {
      // I testi fra i figli, in ordine: uno avvolto per intero, o l'apertura di una frase spezzata da
      // tag e valori che si chiude in un testo successivo dello stesso genitore.
      let aperto = false;
      for (const c of node.children) {
        if (c.type !== "JSXText") continue;
        const grezzo = code.slice(c.start, c.end);
        const t = grezzo.replace(BORDI, "");
        if (t === "") continue;
        const da = c.start + grezzo.indexOf(t);
        const a = da + t.length;
        if (aperto) {
          if (t.endsWith(f.end)) { chiudi(a); aperto = false; count++; }
          continue;
        }
        if (f.wraps(t)) { apri(da); chiudi(a); count++; }
        else if (t.startsWith(f.start)) { apri(da); aperto = true; }
      }
    }
  });

  edits.sort((x, y) => y[0] - x[0]);
  let out = code;
  for (const [s, e, testo] of edits) out = out.slice(0, s) + testo + out.slice(e);
  return { code: out, count };
}
```

Nota: un `"_%_"` solo in un testo JSX, quando inizio e fine di serie coincidono, è l'apertura se nessuno è aperto, altrimenti la
chiusura: è il caso `<p>_%_hi <b>x</b>_%_</p>`, ed è per questo che il ciclo tiene lo stato `aperto` per genitore.

### B.2 Il comando, `export default async function rewriteMarkers({ config, from, write, log })`

**Quando vale.** Si decide al passo 1, con i soli `config.markers` e gli argomenti, **prima di leggere un solo sorgente**: un
comando che si attiva o no a seconda di cosa trova nel codice sarebbe imprevedibile. `from` = argomenti (zero = `_%_`), `to` =
setup.

| Setup (`to`) | Argomenti (`from`) | Esito |
| :- | :- | :- |
| personalizzato `≼≽` | nessuno | `_%_` → `≼≽` (il primo passaggio) |
| personalizzato `≼≽` | `"§"` | `§…§` → `≼≽` (un cambio fra personalizzati) |
| personalizzato `≼≽` | `"≼" "≽"` | inefficace: "nothing to rewrite" (C, variante 1) |
| di serie `_%_` | nessuno | inefficace: "nothing to rewrite" (C, variante 2, che spiega come rientrare) |
| di serie `_%_` | `"≼" "≽"` | `≼≽` → `_%_` (il rientro) |

In una frase: inefficace quando `from` e `to` coincidono. Con il setup di serie succede proprio quando mancano gli argomenti.

Passi, in quest'ordine:

1. `to = config.markers`. `from` è già validato da chi chiama (E.1). Se `from.start === to.start && from.end === to.end` → errore
   "nothing to rewrite" nella variante giusta (Appendice C: setup personalizzato o di serie). Exit 1. Nessun file letto.
2. File: `walkSource(srcRoot, localeDir, baseDir)` come `scanSource`. Per ciascuno: lettura `utf8`; se
   `!mayHaveMarkers(code, from)` salta; `planRewrite` → se `count > 0` tieni `{ path, rel, code, nuovo, count }`. Un file che non si
   parsa **e** contiene i marcatori di partenza (`mayHaveMarkers(code, from)`) **blocca la scrittura**: i suoi marcatori resterebbero
   vecchi senza che il confronto delle chiavi lo veda (non si parsa né prima né dopo). Annotalo e continua la verifica, per elencarli
   tutti alla fine.
3. **Status prima**: per ogni file letto, `extractMarkers(code, { filename, table: prima, rewrite: false, baseDir, autoWrap:
   config.autoWrap, markers: from, warn: () => {} })` e, sulla stessa tabella, con `markers: to` (le stringhe già migrate). Insieme
   = chiavi di `prima`.
4. **Status dopo**: per ogni file, il codice riscritto (o l'originale se non cambia) con `markers: to` → tabella `dopo`.
5. Le tabelle di lingua: `listLanguageFiles(localeDir)` + `readLanguageFile` (come fa `--status`). Per ogni lingua e per ciascuno dei
   due insiemi: tradotte (chiave presente e non `null`), da tradurre (presente e `null`), da sincronizzare (assente).
6. Stampa (Appendice E.3). Se gli insiemi di chiavi differiscono, o differisce un conteggio, **avviso** con le prime 10 chiavi che
   mancano da una parte o dall'altra, ciascuna col file (`table[id]` dà il testo, `onMarker` il file e la riga).
7. `write === false` (dry run): fine. Exit 0 se uguali e nessun file bloccante, 1 altrimenti.
8. `write === true`: i passi 2-6 sono **la stessa verifica globale** del dry run, su tutti i file, e si fa per intero prima della
   prima scrittura. Se diversi, o se c'è un file bloccante (passo 2), **non scrivere niente**: ripeti l'avviso, elenca i file
   bloccanti, stampa "nothing was written" ed esci con 1. Se tutto torna, scrivi ogni file cambiato
   (`fs.writeFileSync(path, nuovo, "utf8")`: cambiano solo i delimitatori, fine riga e BOM restano quelli del file) e stampa il
   riepilogo. Exit 0.
9. **Una scrittura che fallisce a metà** (permessi, file bloccato da un altro programma): fermati, elenca i file scritti e quelli no,
   esci con 1. Lo stato resta coerente: le chiavi sono le stesse nei file scritti e in quelli no, e i marcatori rimasti vecchi danno
   l'avviso `old-marker`. Rilanciare lo stesso comando riprende da lì, perché i file già scritti non contengono più i marcatori di
   partenza. Dillo nel messaggio.

## Appendice C — I messaggi nuovi (inglese, come gli altri)

- **old-marker** (estrazione): `old marker in "src/App.jsx:12:5": "_%_Ciao_%_" uses "_%_", but this project's markers are "≼…≽" —
  nothing was extracted. Run vtranslate-cli --rewriteMarkerDryRun to see what --rewriteMarker would change.`
- **old-marker** (macro, motivo di `<Trans> left as it was`): `an old "_%_" marker: this project uses other delimiters — run
  vtranslate-cli --rewriteMarker`.
- **nothing to rewrite**, variante 1 (setup personalizzato, argomenti uguali): `nothing to rewrite: "≼…≽" are already the markers in
  vite.config. Name the markers your source uses now, if they are not "_%_": --rewriteMarker "§".`
- **nothing to rewrite**, variante 2 (setup di serie, nessun argomento): `nothing to rewrite: vite.config uses the default markers
  ("_%_…_%_"). To switch, set markerStart/markerEnd (or marker) in vite.config first; to go back to "_%_", name the markers your
  source uses now: --rewriteMarker "≼" "≽".`
- **file bloccante**: `N file(s) contain "_%_" markers but could not be parsed, so they could not be rewritten — fix them first
  (listed below). Nothing was written.`
- **scrittura interrotta**: `writing stopped at "src/x.jsx": <errore>. N file(s) were rewritten, M were not (listed below). Keys are
  unchanged either way: fix the problem and run the same command again to finish.`
- **divergenza**: `the rewrite would change what gets translated: N key(s) differ (listed below). Nothing was written.` (in dry run:
  `…would change what gets translated…` senza l'ultima frase).
- **flag combinati**: `--rewriteMarker cannot be combined with --add, --status, --migrate, --fastverify or any llm flag.`

## Appendice D — `idePlugin/src/highlight/projectMarkers.mjs`

```js
// I delimitatori del progetto che contiene un file, per l'evidenziazione (4.7.0). Li dà la sonda di
// vite.config (Projects), la stessa del pannello: vitetranslateConfig.markers, che una libreria
// della 4.7.0 scrive sempre. null finché non si sanno — elenco non ancora calcolato, lettura in
// corso, Restricted Mode, libreria più vecchia — e allora chi colora usa quelli di serie.
//
// Chiedere i delimitatori di un file avvia la lettura del suo progetto, se manca: l'evidenziazione
// parte senza il pannello, e senza questo colorerebbe `_%_` in un progetto che usa altro. In un
// workspace non fidato Projects non esegue vite.config (risponde `untrusted`): nessun rischio nuovo.
import * as vscode from "vscode";
import path from "node:path";

export class ProjectMarkers {
  constructor({ projects }) {
    this.projects = projects;
    this.elenco = null; // l'ultimo elenco dei progetti arrivato, ordinato dal più profondo
    this.emitter = new vscode.EventEmitter();
    this.onDidChange = this.emitter.event;
    this.ascolti = [
      projects.onDidRead(() => this.emitter.fire()),
      projects.onDidChange(() => { this.elenco = null; this.carica(); }),
    ];
    this.carica();
  }

  carica() {
    this.projects.currentList().then((lista) => {
      this.elenco = [...lista].sort((a, b) => b.dir.length - a.dir.length);
      this.emitter.fire();
    }, () => {});
  }

  /** @returns {{ start: string, end: string } | null} */
  markersFor(fsPath) {
    const progetto = this.elenco?.find((p) => fsPath === p.dir || fsPath.startsWith(p.dir + path.sep));
    if (!progetto) return null;
    const letto = this.projects.ready(progetto.dir);
    if (!letto) { this.projects.data(progetto); return null; } // la lettura, quando arriva, fa scattare onDidRead
    return letto.probe?.vitetranslate?.markers ?? null;
  }

  dispose() {
    for (const a of this.ascolti) a.dispose();
    this.emitter.dispose();
  }
}
```

Verifica sui sorgenti (prima di copiarlo): che `currentList()` restituisca oggetti con `dir` e che `onDidChange` di `Projects` scatti
quando l'elenco cambia; su Windows i percorsi di VS Code e quelli di `Projects` devono avere la stessa forma (maiuscola della lettera
di unità): se no, confronta con `path.resolve(...).toLowerCase()` su `win32`. Una contraddizione → ask.

## Appendice E — Il CLI

### E.1 Lettura dei flag

```js
/**
 * `--rewriteMarker [start] [end]` o `--rewriteMarkerDryRun [start] [end]`, senza badare a maiuscole.
 * Gli argomenti sono i marcatori ORA nei sorgenti: nessuno = quelli di serie, uno = lo stesso ai due
 * capi, due = inizio e fine. Si prendono gli argomenti che seguono finché non comincia un `--`: un
 * delimitatore può cominciare con un `-` solo.
 * @returns {null | { dryRun: boolean, from: { start: string, end: string } }}
 */
function collectRewrite(argv) {
  const i = argv.findIndex((a) => ["--rewritemarker", "--rewritemarkerdryrun"].includes(a.toLowerCase()));
  if (i === -1) return null;
  const dryRun = argv[i].toLowerCase() === "--rewritemarkerdryrun";
  const args = [];
  for (let j = i + 1; j < argv.length && !argv[j].startsWith("--"); j++) args.push(argv[j]);
  if (args.length > 2) throw new Error(`${argv[i]} takes at most two markers (start, end): got ${args.length}`);
  const start = args[0] ?? SOURCE_OPEN;
  const end = args[1] ?? args[0] ?? SOURCE_CLOSE;
  const problema = markerProblem(start, "start") ?? markerProblem(end, "end") ?? markerPairProblem(start, end);
  if (problema) throw new Error(`${argv[i]}: ${problema}`);
  return { dryRun, from: { start, end } };
}
```

Più di un flag di riscrittura nella riga di comando → errore (controlla con un `filter` sugli stessi due nomi).

### E.2 Le voci di `HELP`

```
  --rewriteMarker [start] [end]
                  Rewrite the markers in srcDir from the ones named here (default
                  _%_; one argument = same at both ends) to markerStart/markerEnd
                  of vite.config. Does nothing when the two are the same. Checks
                  every file first and writes all or nothing: same keys, same
                  translation status, or not a byte is written. Comments and
                  imports are never touched.
  --rewriteMarkerDryRun [start] [end]
                  The same check, writing nothing: the translation status before
                  and after, and a warning if they differ.
```

### E.3 L'output (nella colonna di log del CLI, come `--status`)

```
rewrite  _%_…_%_  →  ≼…≽          (dry run)
files    12 to change, 47 markers
before   42 keys · en-US 40/42 · zh-CN 42/42
after    42 keys · en-US 40/42 · zh-CN 42/42
ok       same keys, same status — run without DryRun to write
```

Con divergenza, `ok` diventa una riga d'avviso col messaggio dell'Appendice C e l'elenco delle chiavi. Usa le funzioni di log che usa
già `--status` (`logEchoColored`, `logRule`…): la forma precisa la decide il resto del CLI, non questo schizzo.

## Appendice F — La procedura di rinomino (sito, demo, doc)

Per **ogni** file delle cartelle della tabella 5.4 (e per gli esempi di codice in `doc/*.md` e nei README), in quest'ordine, con
Edit o con uno script node che preserva i CRLF:

1. **Import da `@sepoina/vitetranslate/react`**, solo dentro le graffe di quell'import: `TranslateContainer` → `TransContainer`,
   `useTranslateToString` → `useTrans`, `useTranslateLanguage` → `useTransLanguage`, `Translate` → `Trans` (in quest'ordine: i nomi lunghi
   prima, perché `Translate` è prefisso di `TranslateContainer`). Un alias già presente (`Translate as T`) → **lascialo** e annotalo.
2. **JSX**: `<TranslateContainer` → `<TransContainer`, `</TranslateContainer>` → `</TransContainer>`, poi `<Translate` seguito da spazio,
   `/` o `>` → `<Trans`, `</Translate>` → `</Trans>`.
3. **Chiamate**: `useTranslateToString(` → `useTrans(`, `useTranslateLanguage(` → `useTransLanguage(`.
4. **La variabile**: `const ts = useTrans()` → `const trans = useTrans()`; nello **stesso file**, ogni `ts` usato come identificatore
   (`` ts` ``, `ts(`, `ts,`, `{ts}`) → `trans`. Rileggi il file: `ts` può essere altro (un timestamp, `.ts` in una stringa).
5. **Testi che nominano la libreria** dentro un `<Trans>…</Trans>` o un marcatore (es. "Scrivi `<Translate>`…"): cambiali a `<Trans>` **solo** se
   parlano del codice da scrivere, e annota la chiave: è un messaggio nuovo da tradurre (5.4).
6. Nessun nome lungo rimasto fuori dai punti voluti: `grep -rnE "\b(Translate|useTranslateToString|TranslateContainer|useTranslateLanguage)\b"`
   sulla cartella, e per ogni riga una ragione (playEdge, un testo che parla del nome esteso).

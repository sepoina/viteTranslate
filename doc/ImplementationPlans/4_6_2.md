## Il concetto (leggilo prima di scrivere codice)

Per ogni richiesta:

- **O**: l'overhead, cioè il prompt di sistema **che contiene già il contesto** (vedi `buildTranslateSystemPrompt`), in token
  di input. È fisso per lingua e si ripete a ogni lotto.
- **P**: il carico utile, cioè le chiavi del lotto serializzate, in token di input.
- **U**: la risposta attesa, in token di output.

La quota sprecata è `O / (O + P)`. Una classe fissa `k`: il lotto si chiude **appena** `P ≥ k·O`, perché è il lotto più
piccolo con overhead ≤ `1/(1+k)`, e un lotto più piccolo significa meno allucinazioni. Due tetti **rigidi** lo chiudono
prima: `U ≤ maxOutputTokens` (troncamento e qualità) e `chiavi ≤ maxKeys` (qualità).

Le due regole sono di natura diversa, ed è il punto dove è più facile sbagliare:

- `k·O` è una **soglia minima**: si aggiunge la voce, **poi** si controlla se l'hai raggiunta, e in quel caso si chiude.
- `maxOutputTokens` e `maxKeys` sono **soffitti**: si controlla **prima** di aggiungere la voce. Se la voce li farebbe superare,
  si chiude il lotto corrente e la voce apre il successivo.
- Una voce da sola oltre un soffitto va comunque in un lotto da sola: una stringa non si spezza mai (è così anche oggi).

## Fase 1 — Implementazione

### 1.1 `lib/dev/llm/llmOptions.js` — `budget`, `modelClass`, `maxTokensField`

**a) Classi di modello.** Esporta:

```js
export const MODEL_CLASSES = {
  basic:    { k: 1, maxOutputTokens: 1500, maxKeys: 40,  maxTokens: 2048 },
  standard: { k: 3, maxOutputTokens: 3000, maxKeys: 100, maxTokens: 4096 },
  advanced: { k: 4, maxOutputTokens: 4500, maxKeys: 150, maxTokens: 6144 },
  expert:   { k: 5, maxOutputTokens: 6000, maxKeys: 200, maxTokens: 8192 },
  frontier: { k: 6, maxOutputTokens: 8000, maxKeys: 250, maxTokens: 12288 },
};
```

Commento sopra la tabella: i valori sono **stime di partenza**, non misure. `maxTokens` è ciò che si manda al provider e
lascia margine sopra `maxOutputTokens`, che conta anche il ragionamento dei modelli che ragionano: i loro token di pensiero
sono token di output fatturati, e la taratura li include (vedi 1.4).

- Aggiungi `"modelClass"` e `"maxTokensField"` a `CONNECTION_KEYS`.
- `connection.modelClass`:
  - se manca, vale `"standard"`;
  - una stringa fuori tabella dà l'errore `llm.connection.modelClass "x" is not one of "basic", "standard", "advanced", "expert", "frontier".`;
  - un oggetto si fonde sopra `standard`: `{ ...MODEL_CLASSES.standard, ...raw }`, e le chiavi ammesse sono solo le quattro della tabella.
- Validazione dell'oggetto risolto:
  - `k` è un numero in `(0, 20]`;
  - `maxOutputTokens` è un intero ≥ 200;
  - `maxKeys` è un intero in `[1, 1000]`;
  - `maxTokens` è un intero ≥ `maxOutputTokens`. Il messaggio di errore spiega che altrimenti ogni lotto pieno si troncherebbe per costruzione.
- Il risultato normalizzato è `connection.modelClass = { name, k, maxOutputTokens, maxKeys, maxTokens }`, con `name` uguale a `"custom"` per un oggetto.
- `connection.maxTokensField` vale `"max_tokens"` (default), `"max_completion_tokens"` oppure `false`. Qualunque altro valore è un errore.

**b) Budget.** Sostituisci `BUDGET_PRESETS` con:

```js
export const BUDGET_PRESETS = {
  safe:      { cost: { maxCostPerRun: 0.1, maxCostPerDay: 0.5 }, tokens: { maxTokensPerRun: 50000,  maxTokensPerDay: 200000 } },
  normal:    { cost: { maxCostPerRun: 1,   maxCostPerDay: 5 },   tokens: { maxTokensPerRun: 500000, maxTokensPerDay: 2000000 } },
  unlimited: { cost: { maxCostPerRun: Infinity, maxCostPerDay: Infinity }, tokens: { maxTokensPerRun: Infinity, maxTokensPerDay: Infinity } },
};
const BUDGET_KEYS = new Set(["maxCostPerRun", "maxCostPerDay", "maxTokensPerRun", "maxTokensPerDay"]);
```

`normalizeBudget(raw, hasPrices)`: i prezzi vanno calcolati **prima** del budget, quindi sposta la chiamata dopo il calcolo
di `hasCostInput`/`hasCostOutput`, cosa che il codice fa già.

- Un preset (stringa, e `undefined` vale `"safe"`) dà `hasPrices ? preset.cost : preset.tokens`. Si usa una sola unità alla volta.
- Un oggetto:
  - ogni chiave fuori da `BUDGET_KEYS` dà l'errore:
    `llm.budget.<k> is not a recognised option. Budget caps are in cost (maxCostPerRun, maxCostPerDay) or, without prices, in tokens (maxTokensPerRun, maxTokensPerDay) — see doc/llm.md.`
    È così che un `maxKeysPerRun` rimasto dalla 4.6.1 viene fuori;
  - la base è `"safe"`, risolto con la stessa regola, e i campi espliciti la sovrascrivono. Un campo esplicito vale **sempre**,
    anche se è nell'altra unità;
  - `maxCost*` senza prezzi è un errore, come già succede per `maxCostPerRun`;
  - ogni valore deve essere un numero ≥ 0 oppure `Infinity`.
- Il risultato ha sempre le quattro chiavi, e quelle non attive valgono `undefined`. Aggiungi anche `preset: "safe" | "normal" | "unlimited" | "custom"`,
  che serve a `--llm-status`.

**Attenzione alla valuta.** I numeri dei preset sono pensati per valute con la scala del dollaro. Con `costUnity: "¥"` avrebbero
poco senso: basta un commento qui e una riga in `doc/llm.md`, senza logica aggiuntiva.

### 1.2 `lib/dev/llm/costModel.js` — da voci a token, un posto solo

Oggi le formule per stimare una voce vivono in due posti, `estimateRun` e `buildBatches.serializedChars`. Portale in funzioni
esportate da **questo** file e usale ovunque:

```js
export function itemCharsIn(item)  // JSON.stringify({ k: item.key, t: item.text, where: item.where }).length
export function itemCharsOut(item) // item.text.length * OUTPUT_EXPANSION + item.key.length + JSON_OVERHEAD_PER_KEY
```

**Rapporti iniziali per sistema di scrittura:**

```js
const CJK = new Set(["zh", "ja", "ko"]);
export function initialRatio(tag) { return CJK.has(tag.split("-")[0].toLowerCase()) ? 1.5 : CHARS_PER_TOKEN; }
```

Mettici un commento: è un'euristica per il **primo** run, e dal secondo vale la misura.

**`estimateRun` cambia firma.** Riceve i lotti già costruiti per lingua, non più `items` / `contextChars` / `systemChars` / `nBatch`:

```js
estimateRun({ languages: [{ systemChars, batches, ratioIn, ratioOut }] })
// -> { tokensIn, tokensOut } (più charsIn e charsOut, se servono alla trace)
```

- `tokensIn` è, per ogni lingua, `(systemChars · batches.length + Σ itemCharsIn) / ratioIn`.
- `tokensOut` è `Σ itemCharsOut / ratioOut`.
- **Qui si corregge il bug del doppio conteggio.** Oggi `systemChars` contiene già il contesto (lo include `buildTranslateSystemPrompt`)
  e `contextChars` lo aggiunge una seconda volta. `contextChars` sparisce.

`costOf` e `formatCost` restano come sono. Aggiungi `formatTokens` dove serve, perché esiste già.

### 1.3 `lib/dev/llm/buildBatches.js` — lotti in token

La nuova firma:

```js
export default function buildBatches(entries, { overheadTokens, modelClass, ratioIn, ratioOut })
```

- `MAX_BATCH_CHARS` e `MAX_BATCH_ITEMS` spariscono. Aggiorna i test che li importano (vedi Fase 2).
- L'ordinamento resta com'è: `localeCompare(..., "en")`, per il determinismo.
- Per ogni voce: `tIn = itemCharsIn(item) / ratioIn` e `tOut = itemCharsOut(item) / ratioOut`.
- Il ciclo, esattamente in quest'ordine:
  1. se il lotto corrente non è vuoto e `outCorrente + tOut > maxOutputTokens` **oppure** `lunghezza + 1 > maxKeys`, chiudi il lotto;
  2. aggiungi la voce e accumula `inCorrente += tIn` e `outCorrente += tOut`;
  3. se `inCorrente >= k · overheadTokens`, chiudi il lotto.
- Alla fine, un lotto non vuoto si chiude comunque.
- Nel commento di testa spiega la differenza fra la soglia minima (punto 3) e i soffitti (punto 1), con il rimando a questo piano.

**Determinismo:** stesse voci, stesso ledger e stesso contesto danno gli stessi lotti. Il dry-run resta predittivo **a parità di
contesto**: se il run vero rigenera l'abstract, O cambia. È un limite preesistente e lo annota la Fase 4, non questa.

### 1.4 `lib/dev/llm/llmLedger.js` — schema 2, contabilità per richiesta

- `SCHEMA_VERSION = 2`. Un ledger v1 viene letto come assente, perché `leggiJson` fa già così: si perdono la taratura e i contatori
  del giorno dell'aggiornamento. Mettilo in un commento, è accettato.
- `emptyLedger()` restituisce `{ day, costToday: 0, tokensToday: 0, keysToday: 0, models: {}, failures: {}, context: {} }`.
  `keysToday` resta **solo come informazione** per `--llm-status`, non è più un tetto.
- `readLedger` fa il rollover anche di `tokensToday`.
- Sostituisci `recordUsage` con:

  ```js
  export function recordRequest(ledger, { model, tag, usage, cost = 0, charsIn, charsOut, keysAdded = 0 })
  ```

  - `ledger.costToday += cost`, `ledger.tokensToday += usage.tokensIn + usage.tokensOut` e `ledger.keysToday += keysAdded`;
  - `models[model]` diventa `{ charsIn, tokensIn, cachedIn, requests, out: { [tag]: { chars, tokens } } }`;
  - la taratura (`charsIn`, `tokensIn`, `out[tag]`) si aggiorna **solo** se `charsIn`/`charsOut` sono numeri, cioè per le risposte
    riuscite. Costo e token del giorno si aggiornano **sempre**, perché anche un tentativo fallito si paga;
  - `cachedIn += usage.cachedIn ?? 0` si registra e basta, perché la correzione con la cache è fuori perimetro;
  - con `tag` assente, cioè per la chiamata del contesto, la taratura non si tocca.
- `ratiosFor(ledger, model, tag)` restituisce `{ ratioIn?, ratioOut? }`, ciascuno solo se tarato (denominatore > 0).
  Chi chiama ripiega su `initialRatio`.
- `recordFailure`, `clearFailure`, `failureCount` e `recordContextGeneration` restano come sono.

### 1.5 `lib/dev/llm/fetchDriver.js` — `max_tokens`, troncamento, cache

- Una nuova proprietà del parametro: `maxTokens` (numero o `undefined`). Nel body, **prima** di `...connection.providerOptions`:
  `...(connection.maxTokensField && maxTokens ? { [connection.maxTokensField]: maxTokens } : {})`.
  `providerOptions` vince perché viene dopo, e il commento esistente dice già perché.
- Il troncamento: se `json.choices?.[0]?.finish_reason === "length"`, lancia
  `new Error("openai-chat reply truncated: max_tokens reached")` con `error.truncated = true` ed `error.usage = usage`.
  Va controllato **prima** del `JSON.parse` del contenuto.
- Anche gli altri errori **dopo** una risposta 2xx ("was not JSON", "reply was not a JSON object") portano `error.usage = usage`,
  perché quella risposta è stata pagata.
- In `usage` aggiungi `cachedIn: json.usage.prompt_cache_hit_tokens ?? json.usage.prompt_tokens_details?.cached_tokens ?? 0`.
  Il primo campo è di DeepSeek, il secondo di OpenAI.
- Il ritorno della traduzione diventa `{ translations, usage, charsOut: content.length }`.

### 1.8 `lib/dev/llm/translatePass.js` — il cablaggio

1. **I rapporti.** Dopo `readLedger`:
   - `ratioIn = ratiosFor(ledger, model).ratioIn ?? initialRatio(config.sourceLanguage)`;
   - per ogni lingua, `ratioOut(tag) = ratiosFor(ledger, model, tag).ratioOut ?? initialRatio(tag)`;
   - con un driver utente senza `model`, usa la chiave `"custom-driver"`, come già fa `replaceGeneratedRegion`.
2. **La chiamata del contesto.** Nel `callModel` del contesto passa `onUsage` e, per ogni usage, esegui
   `updateLedger(… recordRequest(l, { model, usage, cost }))` senza `tag`: il costo del contesto entra nel giorno. Serve anche
   `maxTokens: llm.connection.modelClass.maxTokens`: il contesto è markdown, e anche lì un troncamento si paga.
3. **I lotti.** `buildBatches(lang.entries, { overheadTokens: systemPromptFor(tag).length / ratioIn, modelClass, ratioIn, ratioOut: ratioOut(tag) })`.
   Stessa cosa per i lotti di riparazione: il loro payload porta anche il `reason`, e la differenza è piccola. Lascialo scritto in un commento.
4. **La stima.** Usa `estimateRun({ languages })` con i lotti appena costruiti. `tokens = tokensIn + tokensOut`.
5. **Le guardie.** `checkCaps({ estimate: { cost: cost?.cost, tokens }, today: { cost: ledger.costToday, tokens: ledger.tokensToday }, budget: llm.budget, auto, costUnity })`.
6. **L'esecuzione.** In `sendBatch`:
   - passa `maxTokens` e `onUsage`;
   - `onUsage` accumula `runState.spent.cost` / `runState.spent.tokens` e i contatori misurati, e scrive nel ledger con
     `recordRequest`. **La taratura (`charsIn`/`charsOut`) si passa solo per il tentativo riuscito**: la
     `systemPrompt.length + userPayload.length` e il `charsOut` del risultato;
   - `keysAdded` si passa **dopo** `apply`, con `counts.filled`, con una seconda `updateLedger` che tocca solo `keysToday`,
     oppure unendo le due chiamate, come ti riesce più leggibile;
   - lo stop a metà run usa il nuovo `shouldStopMidRun`.
7. **Il troncamento a schermo.** Un `error.truncated` arriva a `request.fail(error)` come oggi. In `requestPanel.shortReason`
   aggiungi, **prima** degli altri controlli: `if (error?.truncated) return "truncated";`.
8. **La fine del run.** Il vecchio `recordUsage` sparisce. Resta un `updateLedger` per i fallimenti (`recordFailure`/`clearFailure`)
   e per `models[model].requests`, se non lo incrementi già per richiesta: scegli una strada sola e scrivila nel commento.
9. **La nota di stop.** `panel.note` oggi nomina solo `maxCostPerRun`. Falla nominare il tetto che è scattato davvero:
   `shouldStopMidRun` restituisce il nome del tetto invece di `true`.

## Fuori perimetro (per un piano successivo)

- **La correzione dell'overhead con la cache del provider.** Con DeepSeek e OpenAI il prefisso ripetuto costa circa il 10%.
  I dati (`cachedIn` per modello) si raccolgono da questa versione. Il piano successivo decide, sui numeri veri, se `k` va corretto.
- **Il riequilibrio dei lotti.** Oggi 228 chiavi in `standard` fanno 100 + 100 + 28. Con lo stesso numero di richieste, 76 · 3
  darebbe lotti più piccoli, quindi più qualità a costo invariato.
- **Un troncamento che spezza il lotto a metà e riprova**, invece di lasciarne le chiavi a `null` fino al run successivo.

## Il problema, in concreto

I due emitter attraversano la stessa sequenza di sette passaggi. Sono scritti due volte, in due
file, con due stili di virgolette diversi.

| Passaggio | `Translate.js` | `useTranslateToString.js` |
| --- | --- | --- |
| forma a oggetto `{t,a}` | riga 79 | riga 53 |
| sentinelle e stringa vuota | riga 88 | riga 56 |
| elemento React | riga 98, **lo rende** | riga 62, **è un errore** |
| oggetto senza campo `t` | righe 106-121 | righe 70-78 |
| tupla `[testo, ...args]` | righe 125-143 | righe 85-88 |
| numero come dato di dominio | riga 149 | riga 92 |
| valore che testo non è | riga 152, va a `salvage` | **manca** |

L'ultima riga della tabella è il difetto. Dove `<Translate>` manda a `salvage`, `ts()` non
controlla niente e alla riga 111 fa `String(text)`.

Misurato contro i due emitter con i mark diagnostici **spenti**, cioè una build di produzione
con i default:

| input | `<Translate>` | `ts()` oggi |
| --- | --- | --- |
| `[<b/>]` | `""` | `"[object Object]"` |
| `[() => {}]` | `""` | `"() => {}"` |
| `[]` | `""` | `"undefined"` |
| `[null]` | `""` | `"null"` |
| `true` | `""` | `"true"` |

`ts()` serve `placeholder`, `aria-label` e `title`. Quelle stringhe le legge uno screen reader.

Nessun test copre quei cinque casi: la suite verifica `ts()` solo su input corretti e
sull'elemento React passato in prima posizione. Quindi la correzione **non tocca nessuna
asserzione esistente**, aggiunge soltanto.

## Decisioni già prese (non riaprirle senza ask)

1. **`ts()` si allinea a `<Translate>` rendendo `""`**, non `🚫[func]`. Il glifo diagnostico ha
   senso in un nodo di testo, non dentro un `aria-label`: `badData` resta in `Translate.js` e
   `ts()` non lo importa.
2. **Le vie di salvataggio non si condividono.** `salvage`, `pickSource`, `textOf`, `badData`,
   `badDataKind`, `pickBadData` e `argsOf` restano dov'è: `Translate.js`. `readSource` produce
   un verdetto e basta.
3. **I controlli sulla combinazione delle prop restano in `Translate.js`.** `o` insieme a `t`,
   `t` insieme a `children`, `a` insieme alla forma tupla: sono prop di un componente, e `ts()`
   prende argomenti posizionali. `readSource` non li conosce.
4. **La precedenza degli argomenti resta nel chiamante**, perché le due regole divergono per
   davvero. `<Translate>` rifiuta `a` insieme alla tupla; `ts()` lascia vincere la tupla e
   ricade su `a` quando la tupla non porta argomenti. Vedi Punto 2, sezione "L'ordine conta".
5. **`resolveEntry` prende la guardia, non la tabella compilata.** `__proto__: null` nel modulo
   emesso funziona (verificato: rolldown lo conserva attraverso il minify) ma la tabella la
   compila il bundler del **consumatore**, che questa libreria non controlla. La guardia nel
   runtime è verificabile in casa.

## Punto 1 — `lib/react/readSource.js`, il file nuovo

### Cosa deve rispondere

Tre domande, e nient'altro: che testo c'è, che argomenti porta, e se è utilizzabile. Non decide
cosa farne, perché quello è il punto in cui i due emitter divergono legittimamente.

### La forma di ritorno

Quattro esiti. `kind` è sempre presente, il resto dipende da `kind`.

| `kind` | campi | significato |
| --- | --- | --- |
| `EMPTY` | nessuno | niente da rendere: sentinella, `null`, `undefined`, `""` |
| `ELEMENT` | `node` | un elemento React nella posizione del testo |
| `NOT_TEXT` | `why`, `source` | testo non ce n'è. `why` è `"noField"` o `"badValue"` |
| `TEXT` | `text`, `tuple`, `embedded`, `domain` | c'è del testo |

Sui campi di `TEXT`, che sono i tre che si sbagliano:

- **`text`** è sempre una stringa primitiva. Un `new String("x")` esce già come `"x"`, un numero
  già come `"42"`: chi legge non deve più ricontrollare il tipo.
- **`tuple`** dice se il valore ERA una tupla, **indipendentemente da quanti elementi aveva**.
  Serve a `<Translate>`, che rifiuta `a` insieme alla forma tupla anche quando la tupla ha un
  solo elemento. Dedurlo da `embedded` sarebbe sbagliato: `t={["_%_x_%_"]} a={[1]}` oggi è un
  errore, e con `embedded === undefined` smetterebbe di esserlo.
- **`embedded`** sono gli argomenti che la tupla portava con sé, o `undefined` se non ne portava.
  Mai un array vuoto: la differenza fra "non ne porta" e "ne porta zero" è ciò su cui `ts()`
  decide se usare l'argomento posizionale.
- **`domain`** è `true` per un numero o un bigint. Sono dato di dominio, non testo marcato: si
  rendono così come sono, senza interpolazione e senza prefisso.

### Il file

```js
// Architettura d'insieme: doc/structure.md § "Fase 4 — Runtime: la catena di risoluzione".
// Quel documento è la fonte di verità sul funzionamento della libreria: se cambi il
// comportamento di questo file, aggiornalo nello stesso commit.

import { isValidElement } from "react";
import { fromObjectForm } from "./normalizeSource.js";

// La catena di normalizzazione che <Translate> e ts() attraversano prima di poter risolvere
// qualsiasi cosa. Era scritta due volte, e le due copie sono divergute: dove il componente
// manda a `salvage`, l'hook faceva `String(valore)` e scriveva "[object Object]" dentro un
// aria-label. È lo stesso motivo per cui esiste `interpolate.js`, che era già divergente sugli
// argomenti mancanti — qui la cura si estende al resto della catena.
//
// Questo modulo NON decide cosa fare di un esito: <Translate> rende un nodo e ha una via di
// salvataggio che nomina il valore trovato, ts() deve restituire una stringa primitiva e per
// lei un elemento React è un errore. Quelle due cose restano nei rispettivi file.

export const TEXT = "text";
export const EMPTY = "empty";
export const ELEMENT = "element";
export const NOT_TEXT = "notText";

/**
 * Riduce un valore nella posizione del testo a uno dei quattro esiti.
 *
 * @param {any} value - il valore già scelto fra le prop; la scelta la fa il chiamante
 * @returns {{kind: string, text?: string, tuple?: boolean, embedded?: any[], domain?: boolean,
 *            node?: any, why?: string, source?: any}}
 */
export function readSource(value) {
  const source = fromObjectForm(value);

  // Confronto esplicito e non sulla falsità: `0` e `false` sono entrambi falsy, ma solo il
  // secondo è la sentinella delle prop non passate. Con `!source` un conteggio che valga zero
  // sparirebbe senza che niente lo segnali.
  if (source === false || source === null || source === undefined || source === "") {
    return { kind: EMPTY };
  }

  // Un elemento sa già renderizzarsi. Che sia lecito o no lo decide il chiamante.
  if (isValidElement(source)) return { kind: ELEMENT, node: source };

  // Un oggetto senza campo `t` non è la forma `{ t, a }` e non contiene testo: è "niente",
  // come null. `hasOwn` e non la verità del campo, così `{ t: "" }` resta di questa forma.
  if (
    typeof source === "object" &&
    !Array.isArray(source) &&
    !(source instanceof String) &&
    !Object.hasOwn(source, "t")
  ) {
    return { kind: NOT_TEXT, why: "noField", source };
  }

  const tuple = Array.isArray(source);
  const raw = tuple ? source[0] : source;
  // `undefined` e non `[]` quando la tupla non porta argomenti: è la differenza su cui ts()
  // decide se usare l'argomento posizionale ricevuto a parte.
  const embedded = tuple && source.length > 1 ? source.slice(1) : undefined;

  // Un numero nella posizione del testo è dato di dominio: un conteggio, un interno, un codice.
  // Marcato non può essere — dal sorgente non ci passa — e in "42" segnaposto non ce ne sono.
  if (typeof raw === "number" || typeof raw === "bigint") {
    return { kind: TEXT, text: String(raw), tuple, embedded, domain: true };
  }
  if (typeof raw === "string" || raw instanceof String) {
    return { kind: TEXT, text: String(raw), tuple, embedded, domain: false };
  }

  // Una funzione, un simbolo, un elemento dentro la tupla: testo non ce n'è e non ce ne sarà.
  return { kind: NOT_TEXT, why: "badValue", source };
}
```

### La trappola: `source` in `NOT_TEXT`

`source` è il valore **dopo** `fromObjectForm`, non la prop originale. Serve a `describeValue`
nei messaggi, e va bene così: è il valore su cui la decisione è stata presa. `salvage` invece
riparte dalle prop grezze, che riceve per conto suo — non da qui.

## Punto 2 — `Translate.js` che usa il modulo

### Cosa si toglie

Le righe **79-154**, cioè da `source = fromObjectForm(source)` fino al `return salvage(...)` del
"must be a string". La scelta della prop fra `o`, `t` e `children` (righe 67-76) **resta**.

### Cosa si mette

```js
  const v = readSource(source);

  if (v.kind === EMPTY) return "";

  // Un elemento React non è ambiguo: non può essere un marcatore dimenticato, e sa già
  // renderizzarsi. È il caso della prop che a volte porta testo marcato e a volte un nodo già
  // montato (una voce di menu che per "sto caricando" è uno spinner).
  if (v.kind === ELEMENT) return v.node;

  if (v.kind === NOT_TEXT) {
    if (v.why === "noField") {
      // Chiave statica e valore costruito solo se si stampa: `describeValue` è un
      // JSON.stringify, e questo ramo è un esito normale a runtime, non un errore che
      // qualcuno correggerà.
      reportOnce(
        diag,
        'Translate: object without a "t" field',
        () => `Translate: object without a "t" field is not a { t, a } form and renders empty: ${describeValue(v.source)}`,
      );
      return "";
    }
    return salvage({ t, a, o, children }, lang,
      'Translate: "t" is not a supported form',
      () => `Translate: "t" must be a string, an array or a { t, a } object, got ${describeValue(v.source)}`);
  }

  // `a` insieme alla forma tupla resta un errore, e va deciso PRIMA del numero: oggi
  // `t={[42]} a={[1]}` finisce nel salvataggio e non rende "42". Invertire i due controlli
  // cambierebbe quel caso in silenzio.
  if (v.tuple && a !== false) {
    return salvage({ t, a, o, children }, lang,
      'Translate: "a" with the array form',
      () => `Translate: "a" cannot be set when using the t:${describeValue(t)} array form`);
  }

  if (v.domain) return v.text;

  const text = v.text;
  const args = v.tuple ? (v.embedded ?? []) : (a ?? []);
```

Da `if (isCompiledMarker(text))` in poi il file **non cambia di una riga**.

### L'ordine conta

Tre vincoli d'ordine, e sbagliarne uno cambia il comportamento senza far fallire niente:

1. **`v.tuple && a !== false` prima di `v.domain`.** Vedi il commento nel codice qui sopra.
2. **`EMPTY` prima di `ELEMENT`.** Non è teorico: la sentinella `false` non è un elemento, ma
   invertirli renderebbe l'ordine dipendente da `isValidElement`, che è codice di React.
3. **`args` si calcola dopo il controllo su `v.tuple`**, altrimenti si costruirebbe un array
   per un caso che sta per uscire dal salvataggio.

### Cosa NON deve cambiare

`salvage` e tutto ciò che sta sotto il commento `// --- SALVATAGGIO ---` restano identici. Se
durante l'implementazione sembra necessario toccarli, **è un ask**: vuol dire che il verdetto
di `readSource` non porta abbastanza informazione, e la forma di ritorno va rivista prima.

### Il messaggio in console cambia leggermente

Oggi un valore non testuale produce due messaggi diversi a seconda di dove viene intercettato:
`'Translate: "t" is not a supported form'` per un oggetto, `Translate: "t" or "children" must be
a string, got function` per una funzione. Con un solo `badValue` il messaggio diventa uno, e
nomina il valore con `describeValue` invece del solo `typeof`. È più informativo, non meno.

**Nessun test asserisce il testo di quei messaggi** — verificato: la suite controlla solo
`errori.length > prima`. Non c'è niente da adeguare.

## Punto 3 — `useTranslateToString.js` che usa il modulo

### Cosa si toglie

Le righe **53-92** (da `const source = fromObjectForm(t)` fino al controllo su numero e bigint)
e la riga **111**, che è quella con il difetto.

### Cosa si mette

```js
    const v = readSource(t);

    if (v.kind === EMPTY) return '';

    // Un elemento React qui è un errore legittimo, al contrario che in <Translate>: ts() deve
    // restituire una stringa primitiva, e un nodo montato a stringa non si riduce.
    if (v.kind === ELEMENT) {
      reportOnce(diag, 'useTranslateToString: a React element cannot be reduced to a string, renders empty. Use <Translate> instead.');
      return '';
    }

    // Il ramo che mancava. Senza, `String(text)` scriveva "[object Object]" o il sorgente di
    // una funzione dentro un aria-label, e in produzione — dove `‼️` è spento — ci finiva nudo.
    // Rendere vuoto è la stessa scelta che <Translate> fa in produzione per gli stessi valori.
    if (v.kind === NOT_TEXT) {
      const noField = v.why === 'noField';
      reportOnce(
        diag,
        noField
          ? 'useTranslateToString: object without a "t" field'
          : 'useTranslateToString: "t" is not a supported form',
        () => noField
          ? `useTranslateToString: object without a "t" field is not a { t, a } form and renders empty: ${describeValue(v.source)}`
          : `useTranslateToString: "t" must be a string, a number, a tuple or a { t, a } object, got ${describeValue(v.source)}`,
      );
      return '';
    }

    if (v.domain) return v.text;

    const text = v.text;
    // La tupla vince su ciò che è stato passato a parte, ma solo se porta qualcosa: `{t, a:null}`
    // arriva qui come stringa nuda, e chi ha scritto `ts(x, arg)` intendeva proprio quell'arg.
    const args = v.embedded ?? a;
```

Da `if (text.startsWith('_<_') && text.endsWith('_>_'))` in poi il file non cambia, con **una
sola** differenza: `text` è ora garantito stringa primitiva, quindi il controllo `typeof text ===
'string' &&` davanti allo `startsWith` va tolto, ed è inutile anche il
`typeof text === 'string' ? text : String(text)` della vecchia riga 111, che diventa
`stripSourceMarker(text)`.

### L'asimmetria da conservare

`v.embedded ?? a` in `ts()` contro `v.tuple ? (v.embedded ?? []) : (a ?? [])` in `<Translate>`.
Non è una svista e non va uniformata: `<Translate>` ha già rifiutato la combinazione con un
`salvage`, quindi lì `a` e la tupla non coesistono mai. `ts()` prende argomenti posizionali,
dove passare entrambi è naturale, e la tupla vince solo se porta qualcosa.

## Punto 4 — `TranslateArgs`, che oggi non dice niente

In `lib/react.d.ts:13`:

```ts
export type TranslateArgs = unknown | readonly unknown[];
```

TypeScript riduce `unknown | X` a `unknown`. Il tipo documenta un'intenzione che non applica, e
`ts(x, () => {})` compila senza un rumore: è **lo stesso uso scorretto** che il Punto 3 corregge
a runtime, e stringere il tipo lo intercetta prima.

Sostituzione:

```ts
/**
 * Un valore interpolabile in un `%s`. `ReactNode` e non `unknown`: copre stringhe, numeri,
 * bigint, booleani, `null`, `undefined` ed elementi React — che sono esattamente le cose che
 * la tabella compilata sa mettere in un buco — ed esclude funzioni e simboli, che a runtime
 * finivano stringificati dentro un aria-label.
 */
export type TranslateArg = ReactNode;

/** Un valore solo, oppure la lista dei valori in ordine. */
export type TranslateArgs = TranslateArg | readonly TranslateArg[];
```

### Il costo, dichiarato

`ReactNode` **non** include `Date`, né un oggetto di dominio qualunque. Chi oggi scrive
`ts('_%_visto il %s_%_', new Date())` smette di compilare. A runtime funzionava, producendo un
`String(date)` che dipende dal locale del browser — cioè una data formattata a caso, in una
libreria che esiste per non formattare le cose a caso. Costringere il chiamante a formattarla è
la scelta giusta, ma **è un cambiamento sgradito e va confermato**.

> **ASK all'utente prima di applicare questo punto.** Le alternative sono tre: (a) `ReactNode`
> come sopra; (b) `ReactNode | Date`, che copre il caso concreto e lascia fuori il resto;
> (c) lasciare `unknown` e rinunciare all'intercettazione a compile time.

### Il buco che questo punto scopre

`lib/react.d.ts`, `lib/index.d.ts` e `lib/virtual.d.ts` sono spediti nel pacchetto e **non
vengono mai type-checkati**: in questo repo non c'è TypeScript, e i playground sono `.jsx`.
Qualunque cosa si scriva lì dentro, nessuno se ne accorge finché non lo installa un utente TS.

Non risolverlo dentro questo piano. Appuntarlo in `4_1_0.necessarytest.md` come proposta a sé:
aggiungere `typescript` fra le devDependencies e un test che lancia `tsc --noEmit` su una
fixture `.tsx` di una decina di righe. È una decisione con un costo (una dipendenza in più) e va
presa a parte.

## Punto 5 — `updateKeys` reso puro

`lib/dev/vite/uty/updateKeys.js` oggi cancella chiavi dall'oggetto che riceve **e** restituisce
un oggetto nuovo. Le due cose insieme non servono a nessuno.

Verificato prima di scrivere questo piano:

- in `updateLanguage.js:103` l'argomento `imported` **non viene più letto** dopo la chiamata;
- il test in `languageFileIO.test.mjs:404` asserisce solo l'oggetto **restituito**, mai la
  mutazione dell'argomento;
- non ci sono altri chiamanti.

Quindi la riscrittura è sicura e non richiede modifiche ai test esistenti.

```js
/**
 * Confronta le chiavi di `current` con quelle di `wanted` e restituisce la tabella aggiornata
 * insieme al resoconto. Non tocca gli argomenti.
 *
 * Guarda le CHIAVI, non i valori: un testo sorgente riscritto senza cambiare id non esiste,
 * perché l'id è l'hash del testo.
 *
 * `Object.keys` e `Object.hasOwn` al posto di `for...in` e `in`: quelli guardano anche la
 * catena dei prototipi, e una chiave `toString` in un file scritto a mano non risultava mai in
 * eccesso — quindi non veniva mai tolta e restava nel file per sempre. `parseLanguageFile` le
 * rifiuta già in lettura, ma questa funzione non ha motivo di dipendere da quella difesa.
 *
 * @returns {[{changed: boolean, deleted: string[], added: string[], deletedValues: object}, object]}
 */
export default function updateKeys(current, wanted) {
  const stats = { changed: false, deleted: [], added: [], deletedValues: {} };
  const out = {};

  for (const key of Object.keys(current)) {
    if (Object.hasOwn(wanted, key)) {
      out[key] = current[key];
      continue;
    }
    stats.deletedValues[key] = current[key]; // serve al rilevamento dei rename
    stats.deleted.push(key);
    stats.changed = true;
  }

  for (const key of Object.keys(wanted)) {
    if (Object.hasOwn(current, key)) continue;
    out[key] = wanted[key];
    stats.added.push(key);
    stats.changed = true;
  }

  return [stats, out];
}
```

L'ordine delle chiavi in `out` è lo stesso di prima: prima le sopravvissute nell'ordine
originale, poi le aggiunte. Non è portante — `splitAndSortEntries` riordina comunque — ma
conservarlo è gratis e rende il diff dei file di lingua vuoto invece che rimescolato.

## Punto 6 — `fit()` e l'`Intl.Segmenter`

`lib/utility.js:11` costruisce un `Intl.Segmenter` **a ogni chiamata**, e `fit()` viene chiamata
una volta per riga di log (righe 184 e 236). Misurato: costruirlo ogni volta è 3,2 volte più
lento che riusarlo, circa 11 µs a riga. In valore assoluto è irrilevante, e questo punto sta nel
piano solo perché la correzione è di quattro righe.

```js
// Costruito alla prima chiamata e riusato: `fit` gira una volta per riga di log, e costruire un
// Segmenter costa circa tre volte il lavoro che poi gli si chiede di fare. `null` significa
// "questo runtime non ce l'ha", ed è diverso da `undefined`, che significa "non ancora provato".
let segmenter;
function graphemes(s) {
  if (segmenter === undefined) {
    segmenter = globalThis.Intl?.Segmenter
      ? new Intl.Segmenter("en", { granularity: "grapheme" })
      : null;
  }
  return segmenter ? Array.from(segmenter.segment(s), (x) => x.segment) : Array.from(s);
}
```

`fit` usa `graphemes(s)` al posto delle sue righe 11-16.

Il locale passa da `"it"` a `"en"`. Sulla segmentazione dei grafemi non cambia il risultato, ma
un `"it"` fisso dentro una libreria di internazionalizzazione è una brutta riga da leggere. **Non
mettere `undefined`**: prenderebbe il locale della macchina, e la larghezza delle colonne del log
smetterebbe di essere identica fra la macchina dello sviluppatore e la CI.

## Punto 7 — La guardia sui prototipi in `resolveEntry`

La tabella compilata è un oggetto letterale (vedi la coda di `compileLanguageModule`), quindi
eredita da `Object.prototype`. `resolveEntry` la interroga senza guardia:

```js
const entry = table?.[key] ?? fallbackTable?.[key];
```

Con una chiave che è anche un nome di `Object.prototype`, `entry` è una funzione, e la riga
successiva la **chiama**. Verificato:

| marcatore | oggi |
| --- | --- |
| `_<_toString_>_` | rende `"[object Undefined]"` |
| `_<_valueOf_>_` | **lancia** dentro il render |
| `_<_constructor_>_` | **lancia** dentro il render |

Serve che qualcuno scriva a mano la sintassi interna `_<_..._>_`, quindi la probabilità è bassa:
il compilatore produce sempre chiavi nella forma `Nome_checksum`. Ma rompe l'invariante
dichiarata in testa a `Translate.js` — *gli usi scorretti non lanciano più* — e `prefixFor`,
**nello stesso file**, la guardia con `Object.hasOwn` ce l'ha già. `languageResource.js:21` fa lo
stesso su `languages`, con un commento che spiega esattamente questo rischio.

Sostituzione in `lib/react/resolveEntry.js:67`:

```js
  // Solo le proprietà proprie. La tabella compilata è un oggetto letterale, quindi eredita da
  // Object.prototype: una chiave come "valueOf" restituirebbe una funzione, e la riga sotto la
  // chiamerebbe — cioè un crash al posto di una voce mancante. Stessa guardia che `prefixFor`
  // usa qui sotto e che `languageResource.js` usa su `languages`.
  const entry = ownEntry(table, key) ?? ownEntry(fallbackTable, key);
```

con l'helper accanto a `prefixFor`:

```js
const ownEntry = (table, key) =>
  table !== undefined && table !== null && Object.hasOwn(table, key) ? table[key] : undefined;
```

Costo misurato: circa 17 nanosecondi in più per lettura, contro i 2000 e passa di un render
React di un nodo foglia. Non è un fattore.

## Rischi

| Rischio | Perché è accettabile |
| --- | --- |
| **`ts()` cambia output su cinque input** | Sono tutti usi già scorretti, e l'output vecchio era spazzatura dentro un `aria-label`. Nessun test esistente li copre, quindi non c'è comportamento documentato da rompere. Il rischio residuo è uno snapshot di un consumatore che aveva fotografato il difetto |
| **Il refactoring può rompere l'invariante 11 in silenzio** | È l'unico modo in cui questo piano fa danno senza far fallire niente, ed è la ragione per cui il test relativo entra in scope con i valori attesi già misurati |
| **`TranslateArgs` stretto rifiuta un `Date`** | Dichiarato, e sottoposto ad ask prima di applicarlo. A runtime quel `Date` produceva una data formattata secondo il locale del browser, che in una libreria i18n è un bug in attesa |
| **I `.d.ts` non sono type-checkati da nessuno** | Vero e non risolto qui: è un buco che questo piano **scopre**, non che introduce. Appuntato come proposta a sé |
| **Un file nuovo in `lib/react/`, quindi nel bundle browser** | `readSource.js` non aggiunge codice: sposta righe che erano già nei due emitter, e ne toglie una copia. Il bundle `react.es.js` deve **calare**. Se cresce, qualcosa è stato duplicato invece che spostato |
| **`updateKeys` puro alloca un oggetto in più per lingua** | Gira una volta per file di lingua per sync, su tabelle da qualche centinaio di voci. Non è un percorso caldo |

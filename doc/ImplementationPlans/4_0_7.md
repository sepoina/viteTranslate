## Il problema, in concreto

`__builder__` porta tre campi con tre nature diverse, infilati nello stesso posto:

| Campo | Cos'è | Chi lo legge oggi |
| --- | --- | --- |
| `v` | versione del formato della tabella | `languageStatus.js:127` per l'avviso, `updateLanguage.js:65` come sentinella |
| `languageName` | autonimo, calcolato con `Intl.DisplayNames` | solo `vitetranslate.js:396`, che ha già il fallback |
| `incomplete` | restano chiavi da tradurre | **nessuno**: è scritto e mai riletto per decidere |

Il costo non è la riga sul disco. È che una mappa di stringhe contiene una voce che stringa non
è, quindi ogni iterazione ha bisogno di una guardia:

- `parseLanguageFile.js`: il ramo `BRACE`, il messaggio "solo `__builder__` può contenere un
  oggetto", la guardia sul valore cancellato a mano, e `normalizeBuilder`;
- `serializeLanguageFile.js`: l'omissione di `incomplete: false` e la `splice` della traversa;
- `splitAndSortEntries.js`: le due righe che forzano la chiave in testa;
- `compileTable.js`, `guardMassErase.js`, `migrateLegacyLanguages.js`, `vitetranslate.js`:
  quattro `continue` sulla stessa chiave;
- `cli.js:528`: `Object.keys(...).length - 1`, con il commento che spiega il meno uno;
- `updateKeys.js`: un commento che esiste solo per dire che quella chiave non passa di lì.

C'è anche un effetto sul caso d'uso dichiarato dall'utente. La sezione `to be translated` è
pensata per essere incollata in un LLM, e oggi la prima riga di dati del file è un blob JSON che
un modello a volte prova a tradurre o restituisce storto.

## Decisioni già prese (non riaprirle senza ask)

| Domanda | Decisione |
| --- | --- |
| Dove va la versione | In una riga dell'**intestazione a commento**, non in `node_modules/.viteTranslate` e non in un file committato nuovo |
| Perché non nella cache | Quella cartella è per contratto **mai** fonte di verità: `sessionStore.js:65` non scrive se manca `node_modules`, e ogni lettore funziona a cache vuota. Un dato non ricostruibile lì dentro romperebbe proprio quella proprietà |
| Nome del token | `TableVersion` — versiona il **formato della tabella**, non il file |
| Tipo del valore | **numero**, come oggi. `BUILDER_VERSION` resta numerica e `scan.json` continua a confrontarla con `!==` |
| Quante righe leggibili a macchina | **Una sola, per sempre.** È una regola, e va scritta in `structure.md`. Il giorno che si rende leggibile anche `missing key`, l'intestazione smette di essere decorazione e diventa un file di configurazione |
| `languageName` | **Via.** L'autonimo si ricalcola in Node al momento del manifest |
| `incomplete` | **Via, senza sostituto.** La riscrittura si decide sui byte |
| La sezione `to be translated` | **Invariata**, in entrambi i criteri di split. È una funzionalità, non un residuo |
| I file `.bak-*` | Invariati |

## Il formato nuovo

```yaml
#  -------------------------------------------------
#      italiano (Italia) (sourceLanguage)
#       |    code: it-IT
#       |    missing key: 1
#       |    processed: 2026-09-05 12:37
#       |    TableVersion: 260905
#  -------------------------------------------------
App_18e29q3: "Playground"

#  ----to be translated------------------------------------------
App_1wltsn1: null
```

Tre differenze rispetto a oggi, tutte volute:

1. la riga `TableVersion` in coda al blocco dell'intestazione, dopo `processed`;
2. nessuna voce `__builder__`, quindi **nessuna traversa fra intestazione e prima chiave**: la
   `splice` esisteva solo per inscatolare quella voce, e ora è l'intestazione stessa la scatola;
3. i valori della tabella sono `string` o `null`, senza eccezioni.

## Punto 1 — L'opcode e il parser

### La regex, e l'unica cosa che può andare storta

In `lib/dev/vite/uty/parseLanguageFile.js`, accanto alle altre costanti:

```js
// La riga di intestazione che porta la versione del formato. Ancorata al "#" di inizio riga, e
// fra il "#" e il token ammette SOLO caratteri di decorazione: un commento che nomini
// "TableVersion:" dentro una frase non deve diventare l'opcode.
const TABLE_VERSION_RE = /^#[ \t|.\-]*TableVersion:[ \t]*(\d+)[ \t]*$/;
```

**Il match va fatto dentro il ciclo sulle righe, su righe già classificate come commento. Mai
con una ricerca globale sul testo intero.** Un valore tradotto può contenere quella sequenza
letterale, e una ricerca globale la troverebbe dentro una stringa. È l'unico modo in cui questa
modifica può sbagliare in silenzio, ed è il motivo per cui esiste questo paragrafo.

Nel ciclo, il ramo del commento diventa:

```js
if (first === HASH) {
  // Solo finché non si è trovata: le righe di commento di un file di lingua sono
  // l'intestazione più il separatore, quindi il costo è una manciata di exec per file.
  if (tableVersion === null) {
    const m = TABLE_VERSION_RE.exec(line);
    if (m) tableVersion = Number(m[1]);
  }
  continue;
}
```

con `let tableVersion = null;` dichiarata accanto a `const table = {}`.

Attenzione: il ramo che intercetta le righe indentate (`first === SPACE || first === TAB`) fa
`continue` sui commenti indentati **senza** passare da qui. Va bene: l'intestazione che scriviamo
non è indentata, e un opcode indentato non è un formato che produciamo.

### Il portatore legacy

Un file scritto dalla 4.0.6 o prima non ha il commento e ha la voce. Va letta e scartata, subito
dopo il calcolo di `raw`:

```js
// Portatore legacy della 4.0.6 e precedenti: la versione stava in una voce della tabella. Si
// legge per sapere con quale formato il file è stato scritto, poi si scarta — non è una chiave
// di contenuto, e alla prossima riscrittura non esisterà più. Un valore illeggibile qui non è
// un errore: vale "versione sconosciuta", che porta comunque alla riscrittura.
if (key === BUILDER_KEY) {
  if (tableVersion === null && raw.charCodeAt(0) === BRACE) {
    try { tableVersion = Number(JSON.parse(raw)?.v) || null; } catch { /* versione sconosciuta */ }
  }
  continue;
}
```

Con questo cadono, nello stesso file:

- la guardia `"__builder__" must hold a JSON object`;
- dentro il ramo `BRACE`, il caso `key !== BUILDER_KEY`: ora **nessuna** chiave può contenere un
  oggetto, e il messaggio diventa un solo `throw at(...)` che dice di quotare il testo;
- `normalizeBuilder`, che va **rimossa** insieme al suo export e al suo import in
  `readLanguageFile.js`.

### La forma di ritorno

`parseLanguageFile` restituisce `{ table, meta }`:

```js
// File vuoto: lingua nuova, non un errore.
if (clean.trim() === "") return { table: undefined, meta: { tableVersion: null } };
...
return { table, meta: { tableVersion } };
```

`readLanguageFile` restituisce la stessa coppia e non chiama più `normalizeBuilder`.

**I metadati NON vanno attaccati alla tabella come proprietà non enumerabile.**
`updateLanguage.js:96` e `updateAllSubLanguages.js:108` clonano entrambi con lo spread, e una non
enumerabile lì sparirebbe senza dire niente. La coppia esplicita è l'unica forma sicura.

## Punto 3 — Il confronto sui byte, che manda via `incomplete`

### Perché il flag esiste oggi

Non per dichiarare la completezza. A `updateLanguage.js:139` i vecchi dati vengono **riclassificati
con il criterio attuale** prima del confronto, quindi un cambio di classificazione non si vede: il
flag è l'unica cosa che resta diversa fra i due lati. Stessa storia a
`updateAllSubLanguages.js:151`, per il traduttore che sostituisce i `null` a mano.

### La sostituzione

Si smette di confrontare strutture e si confrontano i byte, mascherando la sola riga del
timestamp. In `lib/dev/vite/uty/buildLanguageHeader.js`, export nuovo:

```js
// La riga del timestamp è la sola parte del file che cambia a ogni sync anche quando il
// contenuto è identico: mascherarla su entrambi i lati rende "questi byte devono cambiare?" una
// domanda con una risposta sola.
//
// Si maschera SOLO quella riga. "missing key" sta nella stessa intestazione ed è proprio il
// segnale che deve far scattare la riscrittura quando cambia solo la classificazione
// tradotto/da tradurre — cioè il lavoro che faceva "incomplete". Mascherare l'intestazione
// intera per comodità rende il confronto cieco esattamente sul caso per cui esiste.
const PROCESSED_RE = /^#.*\bprocessed:.*$/gm;

export const sameIgnoringProcessed = (a, b) =>
  a.replace(PROCESSED_RE, "") === b.replace(PROCESSED_RE, "");
```

Le due regex di questo piano sono già state verificate su tutti i casi della tabella dei test, in
sede di stesura. La `g` è sicura perché `String.replace` azzera `lastIndex`: non usare
`PROCESSED_RE.test()`, che invece non lo fa.

### `updateLanguage.js`

Il testo grezzo va tenuto. Nel ramo del file esistente:

```js
let oldText = null;
...
let imported, meta;
let guasto = null;
try {
  oldText = readLanguageText(filePath);
  ({ table: imported, meta } = readLanguageFile(filePath, oldText));
  if (imported !== undefined && meta.tableVersion === null) {
    throw new Error("no TableVersion header: not a language table");
  }
} catch (e) {
  guasto = e;
  oldText = null; // qualunque guasto forza la riscrittura
}
```

`oldText = null` va messo anche nel ramo `imported === undefined` (file vuoto).

Poi, al posto di `versionEntry`, di `isSameSplit` e del confronto:

```js
const { translated, untranslated } = splitAndSortEntries(baseData, isUntranslated);
const text = serializeLanguageFile({
  tag: sourceLanguage, isSource: true, translated, untranslated, now: new Date(),

const unchanged = oldText !== null && sameIgnoringProcessed(oldText, text);
let written = false;
if (!unchanged && !illeggibile) {
  try { fs.writeFileSync(filePath, text, "utf8"); written = true; }
  catch (e) { logError(`writing in '${colorize("nome", fileName)}': ${e.message}`); }
}
```

Spariscono: la riassegnazione di `baseData["__builder__"]`, `oldBaseData` e il suo clone,
`isSameSplit` e l'import di `stableStringify`.

## Punto 4 — Via `languageName`

In `vitetranslate.js:396`:

```js
const name = JSON.stringify(languageAutonym(tag));
```

Il rischio è stretto e va accettato consapevolmente: su un Node compilato **small-icu**
`Intl.DisplayNames` non risolve, `languageAutonym` ricade sul tag, e il selettore di lingua mostra
`fr-FR` invece di `français (France)`. I binari ufficiali di Node sono full-icu dalla 13, quindi
si parla di Node pacchettizzati dalle distribuzioni.

Mitigazione, in `languageStatus.js`, dentro `statusOfFile`:

```js
// Autonimo uguale al tag: l'ICU di questo Node non conosce la lingua. Non è un errore del
// progetto, ma è ciò che finirà nel selettore di lingua del bundle, quindi va detto.
if (row.language === tag) nota("warning", "no display name for this tag in this Node build: the language list will show the tag");
```

**L'autonimo non va riletto dalla prima riga dell'intestazione.** Quel nome è per le persone: se
diventa leggibile a macchina, chi lo corregge a mano cambia il bundle.

## Punto 5 — Vuoto, svuotato, e la protezione che si perde per strada

Questo punto **non è un dettaglio**: è una regressione che nasce dal togliere `__builder__`, ed è
stata trovata in analisi, non in test.

Oggi `parseLanguageFile` lancia `no entry found` su un file che ha contenuto ma nessuna voce, e
quello è il ramo che manda un file svuotato a mano nel backup invece che nel ripopolamento
silenzioso. Ma oggi `__builder__` **conta come voce**: il file sorgente di un progetto senza
nemmeno un marcatore ha una chiave, quindi non lancia. Tolta la voce, quel file ha zero chiavi e
finirebbe nel ramo del backup a ogni sync, per sempre.

Dalla forma non si distinguono i due casi, perché l'intestazione con `TableVersion` c'è in
entrambi. Si distinguono solo sapendo quante chiavi ha trovato la scansione, e quello lo sa chi
chiama. Quindi:

1. in `parseLanguageFile`, **rimuovere** il `throw` finale su `Object.keys(table).length === 0`.
   Zero voci non è più un errore del parser;
2. in `updateAllSubLanguages`, dopo la lettura riuscita:

```js
// Zero voci non è più un errore del parser: distinguere "tabella legittimamente vuota" da "file
// svuotato a mano" richiede di sapere quante chiavi ha il codice, e lo sa solo chi chiama. Se il
// riferimento ha chiavi e il file no, il file è stato svuotato: si mette al sicuro prima di
// ripopolarlo. Qui il backup conta davvero, perché qui si perdono traduzioni.
if (existingJson !== undefined && Object.keys(existingJson).length === 0 && Object.keys(referenceTable).length > 0) {
  backupLanguageFile(sourceFile, file, testoLetto, { kind: "corrupted", reason: "no entry found: the file has content but not a single key" });
  nota = "was emptied, rebuilt";
  existingJson = {};
}
```

3. in `updateLanguage` **non** serve un ramo equivalente: il file della lingua sorgente è
   integralmente rigenerabile dalla scansione del codice, e un backup di un'intestazione senza
   voci non salva niente. Si lascia che il giro normale lo riscriva.

Effetto collaterale accettato e da testare: `checkSetup` non restituisce più `source-invalid` per
un file sorgente svuotato. Il dev server parte con una tabella vuota, e la sync successiva lo
ricostruisce. È un cancello d'avvio, non una guardia sui dati.

## Punto 6 — Contorno

- **`buildLanguageHeader.js`** importa `BUILDER_VERSION` da `./builderVersion.js` — nessun ciclo,
  quel file non importa niente — e aggiunge la riga `TableVersion` dopo `processed`.
- **`builderVersion.js`**: `BUILDER_VERSION` passa da `260824` a **`260905`**. Senza il bump,
  `fastVerify.js` non invalida `scan.json` e un progetto con cache calda salterebbe il sync di
  migrazione restando sul formato vecchio.
- **`serializeLanguageFile.js`**: via `BUILDER_KEY`, via il caso `incomplete === false`, via la
  `splice` della traversa e via la costante `RULE`.
- **`splitAndSortEntries.js`**: via le due righe `if (a === "__builder__")` nel comparatore, e
  docblock aggiornato.
- **`compileTable.js`**: via `METADATA_KEY` e i due `continue`. Il commento lungo sopra la
  costante spiegava perché quei metadati non finiscono nel bundle: ora non esistono, e va tolto.
- **`migrateLegacyLanguages.js`** è il **secondo scrittore** di file di lingua e si dimentica
  facilmente perché non passa dal giro di sync: il `continue` su `__builder__` in `readLegacyModule`
  resta giusto (i file 3.x quella chiave ce l'hanno), ma il file prodotto deve uscire dal
  serializzatore nuovo, quindi con l'opcode e senza la voce. Verificare a mano su un `.js` 3.x.
- **`cli.js`**: `service.sourceTable` nasce come `{}`, e `chiaviTrovate` diventa

- **`updateKeys.js`**: via il commento su `__builder__`, che ora non descrive più niente.
- **`package.json`**: `version` a `4.0.7`, `versionDescription`:
  `"A language table that holds nothing but text, and a header that carries its own format version."`
- **`README.md`**: nessuna modifica, non nomina `__builder__`. Il limite dei 10 kB non va rimisurato.

| file con contenuto e zero voci | `table` è `{}`, **nessuna eccezione** |
| file vuoto | `table === undefined` |

E la parità con js-yaml, che ora si rafforza: **niente più deroga**, i due parser devono
concordare sull'intera tabella. Aggiungere l'asserzione esplicita che nessun valore della tabella
è un oggetto.

**`serializeLanguageFile`**: il testo prodotto contiene la riga `TableVersion`, **non** contiene
`__builder__`, e fra intestazione e prima chiave non c'è più la traversa. Round-trip: serializza,
rileggi, `meta.tableVersion` uguale a `BUILDER_VERSION`.

**Test nuovo, `headerContract.test.mjs`**: `buildLanguageHeader` produce una riga che
`parseLanguageFile` riconosce. È l'accoppiamento nuovo introdotto da questo piano — il layout
dell'intestazione diventa parte del contratto — e senza questo test si rompe in silenzio il giorno
che qualcuno riallinea le colonne. Nello stesso file: `sameIgnoringProcessed` dice `true` per due
testi che differiscono solo nel timestamp, e `false` se differisce `missing key`.

**`syncPipeline.test.mjs`**: le asserzioni su `t.__builder__.incomplete` (righe 129, 150)
diventano asserzioni sul **file scritto**. Il caso che contava è quello: una sub-lingua che si
completa deve far riscrivere il file della lingua sorgente. Più il caso nuovo, che oggi non è
coperto: **due sync di fila non toccano nessun file**, confrontando gli mtime.

**`languageStatus.test.mjs`** e **`checkSetup.test.mjs`**: l'helper `builder(...)` diventa un
helper che scrive l'intestazione. In `checkSetup`, il caso nuovo: file sorgente svuotato, non è
più `source-invalid`.

**Regressioni da tenere d'occhio**: `compileTable.test.mjs`, `markupParity.test.mjs` e
`extractMarkers.test.mjs` devono passare **invariati**. Se `compileTable.test.mjs` va toccato oltre
la rimozione di `__builder__` dai fixture, qualcosa è stato cambiato che non doveva.

## Rischi

| Rischio | Perché è accettabile |
| --- | --- |
| **L'intestazione diventa parte del contratto**, da decorazione che era | La regex si aggancia al token e non al layout, e `headerContract.test.mjs` la copre. È il costo dichiarato della scelta |
| **Tutti i file di lingua di tutti i progetti vengono riscritti una volta** | È una sync, non una migrazione a parte, e il ramo legacy la rende automatica. Il bump di `BUILDER_VERSION` garantisce che avvenga anche a cache calda |
| **`languageName` via: nomi degradati a tag su Node small-icu** | Binari ufficiali full-icu dalla 13, e l'avviso in `--status` lo rende visibile invece che silenzioso |
| **Zero voci non è più un errore di parse** | La protezione si sposta dove c'è l'informazione per applicarla, ed è più precisa di prima. Copre il caso, oggi rotto per caso, del progetto senza marcatori |
| **Un utente incolla nell'LLM e riceve indietro un file senza intestazione** | Per una sub-lingua non cambia niente: solo `updateLanguage` controlla la sentinella, e il file sorgente è rigenerabile. Da verificare con un test |

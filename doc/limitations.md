# Known limitations

> The [README](../README.md) covers the quick start. This page lists the limitations to be aware of.

> [!WARNING]
> - **Ids are a 32-bit hash** over the file's path and the text. A collision between two strings is unlikely but possible, and reported as a build warning naming both.
> - **Markers must be whole strings.** One embedded in a longer string, or a template literal with `${...}` inside, is not extracted — use a `%s` placeholder instead.
> - **The CLI loads your Vite config with Node itself**, not Vite — a TypeScript config needs a Node that strips types (23.6+).
> - **`basicHtmlToNodes()` still needs the DOM** if called directly. `<Translate>` no longer does.
> - **`autoWrap` only rewrites an attribute — or a JSX text — inside a component it can recognise as such.** The check is per-file and deliberately conservative (see [structure.md](structure.md#autowrap-rewriting-a-marked-jsx-text-or-attribute-430-extended-440)): a function exported as a component, or that already calls a hook, qualifies; one merely *invoked* elsewhere in the same file as a plain function never does, because injecting a hook into it would be an invalid hook call. Unrecognised, the marked text or attribute is left exactly as before this option existed, with an `autowrap-noscope` warning naming the file — `ts()` still works there regardless.
> - **Markup inside a JSX text marker doesn't survive, `autoWrap` or not.** `<p>_%_hi <b>there</b>_%_</p>` is split by the JSX parser itself before extraction ever sees it, and stays a plain string — with `autoWrap` on, a `marker-split` warning names the tag responsible. Not a bug to fix — write the whole text in a string literal (`<Translate t="_%_hi <b>there</b>_%_" />`), or use a `%s` with the tag around the call.
> - **An auto-wrapped text or attribute can't take a `%s` argument.** The call `autoWrap` emits carries no argument list — write `<Translate t={["_%_...%s..._%_", value]} />` or `ts("_%_...%s..._%_", value)` by hand instead. A misused one gets a build-time `autowrap-placeholder` warning, not a silent drop.
> - **`<textarea>` keeps React's own warning even once `autoWrap` translates it.** React rejects children on `<textarea>` regardless of what they are; the translated text does show, but the fix for the warning is `<textarea defaultValue={ts("_%_..._%_")} />`, not `autoWrap`.
> - **An entity and the character it stands for are two different texts to the extractor, everywhere.** `_%_Tom &amp; Jerry_%_` and `_%_Tom & Jerry_%_` get two different ids, exactly like `ts("_%_a &amp; b_%_")` and `ts("_%_a & b_%_")` always have — writing the entity is a choice, not a typo to normalize away.
> - **A fallback embedded in dev can show an un-decoded entity under SSR, until the first sync.** `basicHtmlToNodes()` decodes entities using the DOM; without one (server-side rendering) it returns the fallback text as-is. Gone as soon as the key is synced to the language table — the compiled table never carries this.
> - **LLM auto-translation can't reorder `%s` placeholders.** `lib/react/interpolate.js` substitutes them in order with `list[i++]`; a language that would need the arguments in a different order can't express that. The prompt tells the model to keep the source order and phrase around it, and the validator only checks the *count* — it's a limit of the runtime format, not a bug in the validator (see [the LLM guide](llm.md)).
> - **LLM auto-translation doesn't know about plurals or gender.** The `.yml` format has no notion of either, so there is nothing for the model to fill beyond one string per key.
> - **LLM auto-translation only runs from the CLI, never from `vite dev`.** Wiring it into the plugin would mean a network call — and a bill — on every dev server start. Run `npx vitetranslate --llm-translate` in a second terminal instead; the dev server's watcher picks up the rewritten `.yml` and reloads.

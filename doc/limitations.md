# Known limitations

> The [README](../README.md) covers the quick start. This page lists the limitations to be aware of.

🧪 Most of them run live, one row per case, on the [edge cases page](https://sepoina.github.io/viteTranslate/edge/): seeing the limit is faster than reading it.

> [!WARNING]
> - **Ids are a 32-bit hash** over the file's path and the text. A collision between two strings is unlikely but possible, and reported as a build warning naming both.
> - **Markers must be whole strings.** One embedded in a longer string, or a template literal with `${...}` inside, is not extracted — use a `%s` placeholder instead. 🧪 [Live](https://sepoina.github.io/viteTranslate/edge/#markers).
> - **The CLI loads your Vite config with Node itself**, not Vite — a TypeScript config needs a Node that strips types (23.6+).
> - **`basicHtmlToNodes()` still needs the DOM** if called directly. `<Translate>` no longer does.
> - **`autoWrap` only rewrites an attribute — or a JSX text — inside a component it can recognise as such.** The check is per-file and deliberately conservative (see [structure.md](structure.md#autowrap-rewriting-a-marked-jsx-text-or-attribute-430-extended-440)): a function exported as a component, or that already calls a hook, qualifies; one merely *invoked* elsewhere in the same file as a plain function never does, because injecting a hook into it would be an invalid hook call. Unrecognised, the marked text or attribute is left exactly as before this option existed, with an `autowrap-noscope` warning naming the file — `ts()` still works there regardless. 🧪 This and the next autoWrap limits, live: [edge/#autowrap](https://sepoina.github.io/viteTranslate/edge/#autowrap).
> - **`<textarea>` keeps React's own warning even once `autoWrap` translates it.** React rejects children on `<textarea>` regardless of what they are; the translated text does show, but the fix for the warning is `<textarea defaultValue={ts("_%_..._%_")} />`, not `autoWrap`.
> - **An entity and the character it stands for are two different texts to the extractor, everywhere.** `_%_Tom &amp; Jerry_%_` and `_%_Tom & Jerry_%_` get two different ids, exactly like `ts("_%_a &amp; b_%_")` and `ts("_%_a & b_%_")` always have — writing the entity is a choice, not a typo to normalize away. 🧪 [Entities, live](https://sepoina.github.io/viteTranslate/edge/#html).
> - **A fallback embedded in dev can show an un-decoded entity under SSR, until the first sync.** `basicHtmlToNodes()` decodes entities using the DOM; without one (server-side rendering) it returns the fallback text as-is. Gone as soon as the key is synced to the language table — the compiled table never carries this.
> - **`%s` still can't be reordered.** `lib/react/interpolate.js` substitutes it in order with `list[i++]`; a language that needs a different order can't express that with `%s` — write `{0}`/`{1}` instead, which an LLM translation **can** reorder (see [ICU messages](icu.md)). Left as `%s`, the prompt tells the model to keep the source order and phrase around it, and the validator only checks the *count*. 🧪 [`{0}` in any order, live](https://sepoina.github.io/viteTranslate/edge/#icu).
> - **No ICU apostrophe quoting.** An apostrophe is always text (see [ICU messages](icu.md#apostrophes-are-just-apostrophes)), so messages imported from a standard ICU catalog that use `'{…}'` or `''` need converting: `&#123;…}` for a literal brace, a single `'` for an apostrophe. 🧪 [Live](https://sepoina.github.io/viteTranslate/edge/#icu).
> - **Plurals can't be written as JSX.** A plain value can — `<Translate>Hai {n} messaggi</Translate>` — but `{n, plural, …}` is ICU syntax, not a JSX expression: write `t="…{n, plural, one {# file} other {# files}}…"` or `ts(...)` instead.
> - **A markup tag can't open outside a plural/select branch and close inside it, or the other way round.** Each branch compiles as its own little tree; a tag has to be whole within it — the same limit applies to a numbered tag (a slot).
> - **`<VT.Translate>` isn't recognised.** The preprocessor looks for a plain identifier imported from `@sepoina/vitetranslate/react` (`import { Translate } from …`); a namespace import (`import * as VT from …`, then `<VT.Translate>`) is a different AST shape it doesn't match — same for `Translate` re-exported from a file of your own.
> - **`` ts`…` `` is recognised only when `ts` comes from `useTranslateToString()` in the same file.** Passed as a prop, destructured from a wrapper hook, or imported from another module, the tagged template reaches the runtime uncompiled and is treated as an ordinary, unmarked template — with a console warning in development.
> - **Spread children aren't supported.** `<Translate>Voci {...xs}</Translate>` gets a `macro-unsupported` warning and is left untouched; write the values out, or build the sentence with `ts()`.
> - **`%s` can't appear in the message text.** Inside `<Translate>…</Translate>` or a marked template, write the value as `{value}` — a literal `%s` there is a build error (`percent-s`), not a silent pass-through.
> - **A marked template needs something to receive it.** `` `_%_…${x}_%_` `` compiles only where the `{ t, a }` it produces makes sense: `ts(...)`, `<Translate t={...}>` / `o={...}`, or — with `autoWrap` — a host attribute or child inside a recognised component. Anywhere else it's a build-time `macro-unsupported` warning, and the template is left as it was.
> - **A slot numbers from `1`, not `0`, once the message has a named argument.** Positions and slots share one counter (see [React API](react-api.md#write-jsx-inside-translate)); `<Translate>Ciao {name}, leggi <a href="/d">qui</a></Translate>` compiles the link as `<1>…</1>`, not `<0>…</0>`.
> - **LLM auto-translation only runs from the CLI, never from `vite dev`.** Wiring it into the plugin would mean a network call — and a bill — on every dev server start. Run `npx vitetranslate --llm-translate` in a second terminal instead; the dev server's watcher picks up the rewritten `.yml` and reloads.

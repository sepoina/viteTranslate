## OpenAI-compatible endpoints {#openai-compatible}

The built-in client speaks the Chat Completions shape (`connection.protocol: "openai-chat"`, the only value accepted) with plain `fetch` — no dependency added. ==`/chat/completions` is appended to `baseURL`==. Gemini (`/v1beta/openai`), OpenAI, OpenRouter, Groq, DeepSeek, Ollama, LM Studio and vLLM all work this way: set `connection.baseURL` and `connection.model`, see [setup](/llm/setup#getting-started).

An API that answers in another shape — a different request, a gateway that wraps the reply, a client library — goes through a [custom endpoint](/llm/custom-endpoint).

## Run end to end {#run-end-to-end}

Any OpenAI-compatible endpoint should do. These are the ones run end to end, the most reliable first. The code icon opens a row's setup template: a whole `vite.config.js`, every line of its `llm` block explained, ready to copy. The key goes in a `.env` next to it.

```js id="deepseek" title="vite.config.js"
// Put a .env file in this folder, next to this vite.config.js, holding the key:
//   DEEPSEEK_API_KEY=your-key-here
// and keep it out of git: add .env to .gitignore. Then, from a terminal in this
// folder, check the connection, see what it would cost, translate:
//   npx vitetranslate --llm-ping
//   npx vitetranslate --llm-dry-run --llm-translate
//   npx vitetranslate --llm-translate
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import { vitetranslate } from "@sepoina/vitetranslate";

export default defineConfig({
  plugins: [
    react(),
    vitetranslate({
      localeDir: "locale", // the folder of the translation tables
      sourceLanguage: "en-US", // the language your code is written in
      // Read only by `npx vitetranslate --llm-…`: neither `vite dev` nor the build
      // ever calls the model. Every option, with its default:
      // https://sepoina.github.io/viteTranslate/docs/llm/options/
      llm: {
        connection: {
          // DeepSeek's OpenAI-compatible API: the client adds /chat/completions to
          // it.
          baseURL: "https://api.deepseek.com",
          model: "deepseek-flash",
          // The NAME of the variable that holds the key, never the key: looked up
          // in the environment, then in .env.local and .env in this folder.
          apiKeyEnv: "DEEPSEEK_API_KEY",
          // The price per million tokens, input and output (DeepSeek, October
          // 2026): the estimate, the budget and costGuard count with these.
          costMillionInput: 0.6,
          costMillionOutput: 1.2,
          // How much the model takes at once: batches of up to 100 keys, ~3k output
          // tokens.
          modelClass: "standard",
          // Added as is to every request, and the field is DeepSeek's own.
          // deepseek-flash thinks by default, and the thinking fills the same
          // max_tokens as the reply: translating doesn't need it.
          providerOptions: { thinking: { type: "disabled" } },
        },
        // The spending caps: $1 a run, $5 a day (the "normal" preset, counted with
        // the prices above).
        budget: "normal",
        // Below this estimated cost, in $, the run starts without asking.
        costGuard: 0.2,
        // The context abstract (what the app is about, for the model) writes and
        // refreshes itself.
        context: { mode: "auto" },
      },
    }),
  ],
});
```

```js id="cline" title="vite.config.js"
// Put a .env file in this folder, next to this vite.config.js, holding the key:
//   CLINE_API_KEY=your-key-here
// and keep it out of git: add .env to .gitignore. Then, from a terminal in this
// folder, check the connection, see what it would cost, translate:
//   npx vitetranslate --llm-ping
//   npx vitetranslate --llm-dry-run --llm-translate
//   npx vitetranslate --llm-translate
import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import { vitetranslate } from "@sepoina/vitetranslate";

export default defineConfig({
  plugins: [
    react(),
    vitetranslate({
      localeDir: "locale", // the folder of the translation tables
      sourceLanguage: "en-US", // the language your code is written in
      // Read only by `npx vitetranslate --llm-…`: neither `vite dev` nor the build
      // ever calls the model. Every option, with its default:
      // https://sepoina.github.io/viteTranslate/docs/llm/options/
      llm: {
        connection: {
          // Cline's API speaks Chat Completions but wraps the reply: the driver
          // below reads it.
          baseURL: "https://api.cline.bot/api/v1",
          model: "deepseek/deepseek-v4.1-flash",
          // The NAME of the variable that holds the key, never the key: looked up
          // in the environment, then in .env.local and .env in this folder.
          apiKeyEnv: "CLINE_API_KEY",
          // The price per million tokens, input and output (OpenRouter's for this
          // model, October 2026): the estimate counts with these, then each Cline
          // reply brings the real cost.
          costMillionInput: 0.15,
          costMillionOutput: 0.6,
          // How much the model takes at once: batches of up to 100 keys, ~3k output
          // tokens.
          modelClass: "standard",
          // Added as is to every request: OpenRouter's field, which Cline honours.
          // The model thinks by default, and the thinking fills the same max_tokens
          // as the reply.
          providerOptions: { reasoning: { enabled: false } },
        },
        // A custom LLM driver: the library's fetch brings timeout, retries and the
        // key; the driver sends the built-in request and hands back the text,
        // unwrapped from Cline's { success, data }. Line by line:
        // https://sepoina.github.io/viteTranslate/docs/llm/custom-endpoint/#cline-step-by-step
        driver: async ({
          connection, apiKey, systemPrompt, userPayload, mode, maxTokens, fetch,
        }) => {
          const reply = await fetch(`${connection.baseURL}/chat/completions`, {
            method: "POST",
            headers: {
              Authorization: `Bearer ${apiKey}`,
              "Content-Type": "application/json",
            },
            body: JSON.stringify({
              model: connection.model,
              temperature: connection.temperature,
              messages: [
                { role: "system", content: systemPrompt },
                { role: "user", content: userPayload },
              ],
              ...(mode === "translate"
                ? { response_format: { type: "json_object" } }
                : {}),
              ...(maxTokens ? { max_tokens: maxTokens } : {}),
              ...connection.providerOptions,
            }),
          });
          const { choices: [choice], usage } = (await reply.json()).data;
          return {
            content: choice.message.content ?? "",
            truncated: choice.finish_reason === "length",
            usage,
          };
        },
        // The spending caps: $1 a run, $5 a day (the "normal" preset, counted with
        // the prices above).
        budget: "normal",
        // Below this estimated cost, in $, the run starts without asking.
        costGuard: 0.2,
        // The context abstract (what the app is about, for the model) writes and
        // refreshes itself.
        context: { mode: "auto" },
      },
    }),
  ],
});
```

> [!NOTE] Notes
> ¹ The templates switch reasoning off in `providerOptions` wherever the model has it, and that matters more than it looks. ==A model that thinks by default can spend the whole `max_tokens` thinking and send back an empty reply==, batch after batch — see [reasoning models](/llm/price#reasoning-models). The field is the provider's own: another provider's may be ignored without a word, or turned down with a `400`.
>
> ² For 1000 keys into one language: the model's price per million tokens times what this manual's own translation took per key, ~88 tokens in and ~40 out. Those keys are whole paragraphs: short interface strings cost less.
>
> ³ Five points, minus what went wrong in the runs seen, never below one. Speed, the median per 100 keys: under 10 s nothing, under 20 s −1, under 40 s −2, under 60 s −3, slower −4 (past the default timeout). Retries, batches sent again after a cut-off reply, a timeout or a `429`/`5xx`: some −1, over one batch in ten −2. Errors no check can see: wrong terms −1, wrong names or meaning −2. Only one short run so far: −1. Equal stars, the faster first. Providers have good days and bad ones: the numbers come from a few runs each.
>
> The list grows as endpoints get tested. Got one working that isn't here? [Tell us](https://github.com/sepoina/viteTranslate/issues) the `baseURL`, the model and what you put in `providerOptions`.
